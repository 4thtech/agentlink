Add invites and pairing (M1-7c, 04 §3.6, §3.6.1). `client.pairing.createInvite` makes a single-use invite (1 to 7 days, default 7) and returns its link, the owner fingerprint and the expiry; the store keeps only the encrypted proof key and nonce, never the invite secret. `acceptInvite` decodes the link with the one invite codec (`decodeInviteLink` / `encodeInviteLink`: raw DEFLATE, D-69, with the input bounded before parsing, inflation capped at 16 384 bytes in 1 KiB slices, an exact end of stream and strict UTF-8, I-JSON and schema checks), checks both card signatures, the name and relays and the expiry, and returns `pending_approval` unless the `contacts.acceptInvites` decision allows it; then it stages the pairing and stores the signed handshake. Inbound `handshake` and `handshake-ack` envelopes are handled in `envelopes.processReceived`: the inviter checks the proof, the sender key, the cards, the invite card hash and the commitment, and completes with its ack; the invitee completes only when the ack matches its handshake, the invite card and relays and opens the commitment. A second valid answer to a used invite is refused (`invite_used`). `contacts.completePairing` now binds its evidence to the pairing (the pairing ID is the handshake envelope ID, and the pair must verify as a safety-code transcript), and crossed pairings converge by the later handshake. `pairing.ownerSafetyCode` recomputes the code from the signed messages for owner surfaces only; `recomputeSafetyCode` and `verifyPairingTranscript` are exported. `restrictName` and `renderContactName` implement the contact-name rule, and `ContactView` gains `display`. `safetyCodeChecked` is now always false until `contact.check` verification lands (M1-7c-b).
