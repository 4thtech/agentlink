## Decision

**One deployer key and one address set for testnet and mainnet (amends D-63 (3)).** (1) **Owner decision (Tali, in chat, 14 Oct 2026):** the new campaign deployer key, created by the owner on 14 Oct 2026 (fresh, testnet campaign), will also be the mainnet deployment key. The owner knows the risks and will reassess before the mainnet deployment; if he deems the risk too high, the key is switched before deployment. **Against the documented default:** before the decision the orchestrator advised against it and explained the risk, recommending either a fresh hardware-backed mainnet key (`release-and-deployment.md` §4.3) or one hardware wallet for both campaigns. The owner chose this option knowingly. (2) **Owner decision (Tali, in chat, 14 Oct 2026):** "Let's keep the same address for testnet and mainnet." Testnets and mainnets use one shared CREATE3 campaign label, so with the shared key the contract addresses are identical on testnet and mainnet, across all chains. This decides the review's open item that one shared label would be a separate decision. **Supersedes, unless the key is switched:** the rule that the mainnet deployer key is a fresh hardware-backed key that never touches GitHub (`release-and-deployment.md` §3 rules 2 and 5, §3.2, §4.3, §6, §9 "Mainnet keys never touch GitHub"; 05 §9, §9.1 control 2); the rule that testnet and production never share keys, for the deployer key only (`release-and-deployment.md` §1); the rule that the testnet key is testnet-only and never reused on mainnet (`release-and-deployment.md` §4.2); and the statements that testnet and mainnet addresses differ (05 §9.1; 03 §7 "the testnet and mainnet sets differ"). **Derived (proposed; owner confirms at merge):** *the condition implementing (1):* a mandatory `release-and-deployment.md` §4.3 prerequisite in which the owner reassesses the key, records go or switch in the deploy record and confirms that the mainnet label equals the final testnet campaign label. It fails closed: a known or suspected compromise, an unconfirmed deletion of the CI secret after any window, any deployer activity (nonce or balance change) not explained by a recorded deploy window or funding, or code or a nonzero nonce at any planned mainnet address forces a switch (new key and new label, so new addresses); the owner may choose go only when none applies, and records why. *From (2), in 05 §9.1:* (i) addresses are identical on every testnet and mainnet chain; (ii) the squat risk of the whole testnet phase applies directly to the mainnet addresses, because the key sits in CI during testnet deploy windows: anyone who obtains it can put any code at our addresses on every chain not yet deployed, including future M4 chains; (iii) CREATE3 addresses are single-use per label on each chain: upgrades through the existing proxies keep the addresses, a full testnet redeploy (such as a storage redesign) needs a new label, and mainnet then uses the label of the final testnet campaign, so its addresses match the latest testnet deployment; a key compromise changes both the key and the label, and so the addresses; (iv) clients still map addresses per chain ID, and a testnet proof is not a mainnet proof (the verify page and `agentlink verify` label testnet chain IDs prominently); the testnet campaign no longer ends at M3 (it is the mainnet campaign); the one-shot stage is sized for every chain of the campaign, mainnets and planned M4 chains included, and for the audited build, and its guard layout and labels are frozen from M1-3g. If the key is switched before mainnet, the mainnet addresses differ from the testnet addresses unless the testnets are redeployed under the new key. Mainnet deploys stay manual by the owner with a witness; the key is not hardware-backed unless switched. **Mitigations (proposed; owner confirms at merge; `release-and-deployment.md` §4.2):** (a) the key is a GitHub secret only during a testnet deploy window and is deleted right after the run (amended by D-71 (1)); (b) the private key is never imported into a browser extension or hot wallet; funding a deploy needs only its address; (c) the owner keeps an offline backup; (d) it holds no role after any deploy, as the deployer-holds-no-role check already requires; (e) the risk is reassessed at the start of M3 at the latest, in addition to the mandatory go-or-switch check in §4.3; (f) monitoring (§7.1) from the first deploy window: the deployer address's nonce and balance on every planned testnet and mainnet, including the planned M4 chains, and code at every planned address on every mainnet; any change outside a recorded deploy window or funding is an incident and forces a switch (§4.3); (g) each window is funded with only the gas it needs, and the remainder is swept afterwards; (h) CI hardening while the secret is stored: the deploy job uses only first-party actions pinned by commit SHA, installs nothing from the network once the secret is in scope and never echoes it, and the owner reviews the GitHub audit log and the workflow runs of each window; (i) any terminal scrollback, shell history or log that ever showed the key is cleared, and the owner confirms the key appears in none of them; (j) on go, the key stays used for nothing but deploying this campaign; (k) after the M3 mainnet deploy, any remaining testnet stage (the M2 Registry stage if still pending, M4 testnets) is deployed by the owner locally with the §4.3 procedure and no GitHub secret, because every CI window would expose the mainnet addresses not yet deployed.
