# D-141: Renames reach contacts: a rename re-signs the agent's card with the new name, and the existing card update tells every contact

- **Date:** 2026-10-29
- **Specs:** 04, 06, 07, 08, 11
- **Index:** [all decisions](README.md)

## Decision

**Renames reach contacts: a rename re-signs the agent's card with the new name, and the existing card update tells every contact (W6, B10; amends the "fixed at creation" rule of D-138, U3-d-b).** **Decided by Tali in chat, 2026-10-29** (Decision 43, W6: renames reach contacts through signed card updates, with a Fable review). *Details proposed, owner confirms at merge (W4-RENAME-REACHES-CONTACTS):* (1) **A rename is a key rotation** (04 §2.6), like a relay change (07 §4.3): a new card with the new `nameHash` at `keyEpoch` + 1, carried by the existing `card-update` to each contact and on the owner channel. No new envelope type, signed object or counter. *Alternative not chosen:* (b) a separate owner-signed name object that keeps the keys. It would need a new signed object, receiver rules, a replay counter and an I-4 entry, and the card (so every new proof pack and invite) would still name the old name. (a) reuses a reviewed path end to end; its cost, new agent keys on each rename, is bounded by (4). (2) **Who signs:** the owner, in the same presence gesture that signs `agent.label` (one owner operation, 04 §2.5 "One entry"); the agent key signs only the envelope, `cardAgentSig` and `cardPop`. Renames stay owner-only, in the app; no MCP tool and no CLI command renames an agent or changes its card (I-4). (3) A rename to the name the current card already has changes only the label (no rotation); this is also the repair after a failed label write. (4) **Limit:** at most 3 renames that rotate per agent in any rolling 24 h, refused before the gesture (`rename_limited`); a store-held cost bound, not a security boundary (Q2, decided by Tali in chat, 2026-10-29, Decision 46). (5) **What contacts see:** "{new} (was {old})" once, both under the name rule (06 §2.1), then "{new}"; with the owner's own alias for that contact the alias stays and the note reads "Now calls itself {new} (was {old})"; an Activity entry stays. (6) **Order and catch-up:** the card's `keyEpoch` is the counter (strictly greater, 04 §3.4.1), so the newest rename wins whatever order copies arrive in. Offline contacts catch up through the per-contact sender pass; a contact that still encrypts to a superseded key of this agent is sent the current card again, at most once per 24 h. (7) Agents renamed before this change are not re-published by themselves: the Agents page offers "Update contacts" once; an automatic re-publish would rotate keys without the owner's gesture (Q1, decided by Tali in chat, 2026-10-29, Decision 46). A rename changes neither the safety code nor "Safety code checked", and shows no key warning. Spec: 04 §2.5.1, §2.6, §3.4.1; 06 §6; 07 §3, §4.3; 08 §1; 11 §5.8.
