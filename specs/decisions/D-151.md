## Decision

**One update key for the desktop app, held by CI behind the owner's approval click (UPD-0; amends D-145 (5) and Q-145-3/Q-145-4).** **Decided by Tali in chat, 2026-11-13:** one update-signing key, held as the GitHub environment secret `DESKTOP_UPDATE_KEY` in the environment `desktop-update` (Tali the required reviewer, branch `main` only), used only after his approval click; the same trust as npm `latest`; no USB ceremony and no offline root key. (1) **Key.** The owner creates it once on his own computer with `tools/desktop/new-update-key.mjs` (refuses to run in CI; writes only the private key to a new 0600 file; prints only the public key and the next steps), pastes it into the environment secret, and the public key is pinned in `apps/desktop/src/main/updater/root-key.json` by a PR he checks character by character. The pin files are a sensitive path (CODEOWNERS, `review-gate`; Fable L3). (2) **Signing.** `release.yml`, push to `main` only, after the app is attached and the Release marked Latest, and only when both Mac builds have updates on: `desktop-update-manifest` (no secret, read-only) builds the v2 manifest from the assets downloaded from the Release (SHA-256 checked, build provenance attestation of `desktop.yml` verified) and checks that both builds carry exactly the pin of `root-key.json`; `sign-update-manifest` (environment `desktop-update`, `contents: write` only, checks out the pushed commit, builds the app's verifier before the key is read) reads the key in **one step** from one env var, masks it, refuses a key that is not the pin, signs through `@4thtech-io/crypto` (channel `stable`, valid 30 days, at most 31), then runs the app's own parser on the exact bytes; a bad or unsigned manifest stops the job before the upload. It publishes `desktop-update-<key id>.json` (key id = first 16 hex of the public key, Fable M1) and the same bytes as `desktop-update.json`; the app fetches `releases/latest/download/desktop-update-<key id of its pin>.json`. A daily workflow without a secret goes red 7 days before the document expires; `desktop-update-renew.yml` (dispatch only, same environment) re-signs the Latest release from its attested assets. IR-UPD-8-1: the attestations must come from `desktop.yml` at the released commit of `main`, the Release files must equal this run's build, and a no-secret job checks the environment's rules before any job can reach the key. (3) **Trade-off, accepted by the owner.** No field revocation: a key cannot be withdrawn from installed apps; it is replaced only by a release that pins a new one, which apps with the old pin install by hand (a one-release bridge signed by the old key is a follow-up). A stolen key plus write access to the Releases can ship code to apps that trust it: the same trust as npm `latest` and `npx …@latest` today (04 §7). Mitigations: the approval click, the environment branch rule, one step with the key, the pin check at build and release, attestation checks, `DEPLOY_FREEZE`, the 31-day document expiry. Spec: 04 §7; 08 §8; RB-23 (`docs/runbooks/desktop-update-keys.md`). Cards: UPD-0, UPD-3, UPD-KEYTOOL. Numbering: D-150 is the owner-attach decision on another branch. Invariants I-1 to I-10 unchanged.
