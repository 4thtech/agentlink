## Decision

**Live AI-app status and Pause: every MCP process keeps a heartbeat row, the app reads a live event stream, and the owner can pause an agent (wave 4, 0.4.6).** **Decided by Tali in chat, 2026-10-30** (orchestrator Decision 49: wave 4 gets live AI-app status, after the owner's test showed the app does not notice when an AI app is closed or started; Q7: pausing an agent becomes a feature). *Details proposed, owner confirms at merge (W4-LIVE-STATUS, W4-PAUSE):* (1) **Heartbeat.** Every `agentlink mcp` process, lease holder or not, keeps one row in its agent's store table `mcp_sessions` (07 §3.2): a random session ID, the AI app id mapped from MCP `clientInfo.name` to the fixed table of 06 §7 (else `other`), the agent ID, its pid, start time, `beat_until` and the last tool call time. It beats every 15 s with a TTL of 45 s and deletes the row on clean exit; readers drop a row whose TTL has passed or whose pid is gone (signal 0 only), so a quit or crash shows within about 2 s on this machine and within 45 s at worst. `mcp_last_seen` keeps one "last seen" time per AI app. (2) **States.** `GET /api/ui/agents` adds per agent and per AI app a state: `not_set_up`, `not_running` (with last seen), `working` (a tool call within 60 s), `ready`, `idle` (no tool call for more than 10 min), and per agent `paused` and `offline`. Running now comes from these rows; config entries say only what is set up. (3) **Event stream.** `GET /api/ui/events` sends server-sent events behind the unchanged session, CSRF, `Host`, fetch-metadata and loopback gate of every `/api/ui/` read; the page reads it with `fetch` (not `EventSource`), so the CSRF header is sent and no new way to authenticate is added. It sends only changes, with allowlisted fields (agent names, labels, app ids, states, unix times; never paths, pids, session or holder IDs, agent IDs, keys or message content), event IDs with a 64-event replay buffer for `Last-Event-ID`, a comment every 15 s, at most 4 streams per page session and 8 in all, each closed after 30 min. The page keeps one shared subscription and falls back to polling `GET /api/ui/agents` every 5 s while the tab is visible. (4) **The publisher lease is unchanged** (who subscribes and runs the loop; the host's pairing passes still yield to it); it no longer decides what the app calls Running. (5) **Pause** (Q7). A paused agent sends and receives nothing in any AI app until the owner resumes it in the app: send and fetch tools answer `rejected` with code `AGENT_PAUSED`, queued items wait, relay subscriptions close and no fetch or processing runs; read tools answer from the store. Pause is one click with no Touch ID (it only removes capability), and Resume needs Touch ID and signs the new local owner action `agent.resume`. No MCP tool pauses or resumes (I-4), and the tool surface is unchanged. **Threat note (author):** the stream is a read route and adds no authority; its fields carry no secret (I-7); `clientInfo.name` is untrusted and only its mapped id is kept (I-5); a same-user process can forge or delete heartbeat rows and delete the pause row, which fakes a status or ends a pause but never approves or signs anything (G-1). (6) **Decided by Tali in chat, 2026-10-30** (orchestrator Decision 50, "Approve all"), resolving the open questions: **Q-143-1** Pause is one click, Resume needs Touch ID and signs `agent.resume`; **Q-143-2** sends while paused are refused with `AGENT_PAUSED`, and items already queued wait until resume; **Q-143-3** Pause is per agent, in every AI app, and the owner disconnects an app to stop that app only; **Q-143-4** AI apps not in the table show as "Another AI app". Spec: 04 §2.5, §2.5.1, §4; 06 §6; 07 §3.2; 08 §1. Cards: W4-LIVE-STATUS, W4-PAUSE. Invariants I-1 to I-10 unchanged.
