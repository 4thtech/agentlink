## Decision

**Desktop apps for macOS and Windows (M2-11a, WP-D0): an Electron shell around the unchanged Node core, AI apps keep one stdio MCP process each, owner presence in three phases, and update keys held offline.** **Owner direction, Tali in chat, 2026-11-12:** build the Mac and Windows apps now and in parallel, Linux last; early builds are **unsigned** (macOS "Open Anyway", Windows "More info → Run anyway"); the signing step exists but is off. **Architecture decided by Tali in chat, 2026-11-12** ("Approve all six": the six owner decisions of the desktop plan, revision 1, after an independent Fable review; Q-145-1 to Q-145-6 below). *Details proposed, owner confirms at merge:* (1) **Framework.** A thin Electron main process (window, tray, notifications, `agentlink://` links, single instance, login item, updater) around the **same `@4thtech-io/agentlink` package npm ships**, running on a bundled, hash-pinned official Node.js, installed with `--ignore-scripts` for the target OS and CPU. No `electron`, `electron-builder`, `@electron/packager` or `@electron/get` package; Electron and Node assets are fetched over HTTPS against per-asset SHA-256 committed in the repo; upstream signatures are kept; build-time devDeps only `@electron/asar` and `@electron/fuses`; an Electron security fix ships within 7 days. Tauri was not chosen: a Rust crate supply chain in the shipped binary, no macOS driver for e2e tests, and neither shell gets the macOS Touch ID passkey unsigned (03 §6, 08 §8). (2) **Process model.** The shell holds no keys, no store and signs nothing in phases 1 and 2. It supervises one **core desktop host** (a hidden entry, not a command) that runs the existing app host and talks to the shell over a private pipe (inherited fd 3, JSON lines, fixed message types, strict parsing); the session link travels only over that pipe. AI apps keep **one stdio MCP process each**, started from the absolute bundled `node` and CLI inside the installed app; the 08 §8 stdio→IPC relay is **deferred** (it adds attack surface, and the running app host already syncs the inbox), to be revisited at M2-GATE. Same `~/.agentlink` and keychain service, so there is no data migration; AI-app configs switch to the app form only after the person confirms the diff (06 §7). (3) **Owner presence in three phases, never weaker than today.** *Phase 1 (unsigned):* the existing owner pages inside the app window, presence enforced server-side (D-118); on macOS the default is "Use Touch ID", which opens that one step in the default browser (opening adds no authority, 04 §2.5); on Windows, Windows Hello in the window (expected, pending spike DESK-D1a); the backup code is the fallback. *Phase 2 (unsigned, native helpers):* first-party Secure Enclave (macOS) and Windows Hello `KeyCredential` (Windows) helpers release a wrapping secret for a new owner blob `ALKH` v1 (spec WP-D12a, 04 §2.3.x): a per-install random peer key or challenge stored with the blob, HKDF info binding the blob version, the credential and the owner public key, a TPM-backed key required on Windows, RSA PKCS#1 v1.5 / SHA-256 fixed. **While builds are unsigned this is equal to the WebAuthn PRF path, not stronger**: a same-user process can run the helper and get the secret after the owner's gesture; it fixes "Windows Hello gives no PRF" and names AgentLink in an OS-drawn prompt. *Phase 3 (signed):* the owner key is unlocked only by a **fixed-identity owner process** (an Electron `utilityProcess` from the integrity-checked ASAR, RunAsNode, `NODE_OPTIONS` and inspect fuses off, the keychain access group only on that identity); the bundled generic `node` gets no entitlements, never sees the owner seed, and asks the owner process for each owner operation, which signs and returns the `SignedOwnerAction`; helpers check their caller's code signature. Only phase 3 can retire G-1 (04 §2.5) at M2-GATE: its exit test is that a script run by the signed bundled `node`, and a re-signed or modified build, cannot unlock the owner key. (4) **Release-build lockdown.** Fuses (RunAsNode, `NODE_OPTIONS`, inspect args off; ASAR integrity and only-load-from-ASAR on; cookie encryption on) read back by CI; main exits on any Chromium or Electron switch outside a small allowlist; the preview mode is compiled out of release builds; the scheme is registered as `"<exe>" -- "%1"` and only the one `agentlink://` argument after `--` is read; the window is sandboxed with context isolation, no Node integration, no preload API, an in-memory session, an origin lock and no devtools. (5) **Updates (08 §8).** No update key is ever held by CI. An **offline root key** pinned in the app from the first build signs only key statements; an **offline update key** signs each release manifest on the owner's computer. Manifests carry a domain tag, channel, version, minimum version, expiry and per-asset platform, arch, URL, SHA-256 and size, and are parsed strictly (D-128). Phase 1 shows "Update available" and makes a verified download that the user installs; no silent install or bundle swap until the key ceremony, the independent audit and a rehearsed rotation. Desktop assets ride the npm `latest` approval; `DEPLOY_FREEZE` stops them. (6) **External-build gate.** No build reaches anyone but the owner before the phase-1 updater (WP-D10) and the independent Fable audit (WP-D15, Highs fixed) have landed and the offline key ceremony is done. (7) **Invite links.** `agentlink://join#<fragment>` from the invite page next to the command and "Get the app"; the shell rebuilds the canonical `https://agentlink.4thtech.io/i#…`, checks it against the `join` pattern and passes it over the pipe; accepting needs presence; the link is never logged (08 §4). (8) **Signing.** Early builds are unsigned; only our outer bundle and helpers are ad-hoc signed; the signing jobs exist and stay off (`vars.DESKTOP_SIGNING`, protected `desktop-signing` environment). **Owner decisions (desktop plan §5), decided by Tali in chat, 2026-11-12 ("Approve all six"):** **Q-145-1** the architecture (1)–(3) is approved: Electron shell with the bundled Node core, per-harness stdio MCP kept with the relay deferred, the three presence phases and the phase-3 fixed-identity owner process; **Q-145-2** presence on macOS is biometrics only: in phase 1 the default is Touch ID in the browser (the app's "Use Touch ID" opens that step there), in phase 2 the Secure Enclave helper with `.biometryCurrentSet`; the backup code (master code, D-146) is the fallback, not the device password; **Q-145-3** offline update keys: the owner generates the root and update keys once on his own computer, offline, with two backups, hands over the two public keys, signs each release manifest in the same sitting as the npm `latest` click, and rehearses one rotation before external builds; nothing goes external until this is done; **Q-145-4** the external-build gate of (6) is confirmed, and after it each beta prerelease needs the owner's offline signature, which is itself the approval; **Q-145-5** start **Azure Trusted Signing** now; **Apple Developer ID later**: not needed in this phase, early-adopter Mac builds are unsigned with "Open Anyway" instructions (as with the owner's Curator Mac app), so phase 3 on macOS waits for it; until Windows signing is on, Smart App Control PCs are sent to the one-line installer (if spike WP-D1f shows it works) or told to wait, never told to turn it off; **Q-145-6** bundle ID `io.4thtech.agentlink` and app name "AgentLink", permanent once signed. Spec: 03 §3, §6; 04 §2.2, §2.5, §7; 08 §8; audit-rules §2.2 (`apps/desktop/**`, `apps/cli/src/desktop/**` S2). Cards: DESK-D0 to DESK-D18 (backlog, splitting M2-11a to M2-11f). Amends D-36 (the desktop model now comes in phases; the 08 §8 relay deferred). Invariants I-1 to I-10 unchanged.
