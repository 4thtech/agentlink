# D-111: Top-up and own-account connection: direction

- **Status:** Decided (owner, 20 Oct 2026): points 5–8 decided; points 1–4 direction (proposed)
- **Date:** 2026-10-20
- **Specs:** 06, 08, 11, 12
- **Index:** [all decisions](README.md)

## Decision

**Top-up and own-account connection: direction.** **Decided by Tali in chat, 2026-10-20 (direction only):** "if user already has funds on a specific network, then of course this is the best way. We just need to somehow enable him or her to connect to the wallet that exists in a best possible UI UX way ... and then we need a top-up page ... where user can add credits by credit card, the more simpler, or by transferring funds". Points 1–4 are **direction (proposed)**, derived by the author; only the owner's words are decided. (1) *Proposed:* the pay page (08 §2.3) offers, crypto first, **use crypto you already have** (connect the user's own account), **send to the agent's address** (address and QR code, the network named, for exchanges), and, last, **pay by card** (through a regulated provider that delivers a US-dollar stablecoin to the agent's address, or a 4thTech merchant account; open). Free test credits stay first on testnets. (2) *Proposed targets:* a short path from "needs credits" to credits, network detection from where the funds are and a single confirmation for the own-account path; amounts in $ only and no network choice on the default path (D-39, D-40). (3) *Proposed:* zero access: the pay page and any provider get only the agent's address and an amount. (4) *Proposed:* each method states its privacy effect once (D-109). Not decided, listed as open with recommendations in `project/design/topup-ux.md`: the card approach and provider (M2-18a; also D-15, D-47, M3-7), the connect-method wording (11 §5.1), the top-up link format (M1-26-d; decided, D-113), minimums, and who pays for receipts when the recipient has no credits on the record's network (M1-34; answered, D-114). **Follow-up, decided by Tali in chat, 2026-10-20:** "Realistically, for the card provider, this is the hardest part. So I still don't know how will we solve it, on which legal entity will we use to solve this. So let's keep this as the last step. Let's make it usable and workable without a card first. So crypto is permissionless, so anybody can sign the transaction. We just must make best possible UI UX experience. In regards to the cost, all the costs must be paid by the users. We are not paying for them. So this will be used by agents on behalf of users, people. So agents can perform some such tasks. They can abstract some of the complexities. So let's think in this way." (5) **Card last:** the card path comes after the legal entity is decided (D-15) and after the crypto paths are live; its approach and provider stay open (M2-18a, M3-4c). (6) **Crypto first:** the pay page and the agent flows work without cards. (7) **Users pay every cost:** fees, network costs and receipts are user-paid; 4thTech subsidises none; the testnet faucet is the only exception (12 §1). **OPEN (owner):** (a) the network cost of gasless top-ups, which the submitter pays today (12 §4.5; still open). (b) *Answered, 2026-10-21 (D-112):* "users pay all costs" does not cover messages and files, which stay free; it covers proofs, receipts and top-ups only. (8) **Agent-assisted funding:** the agent explains the one step, gives the link or the address and QR, watches for the funds and confirms the credits; it never holds or asks for the user's keys and never moves the user's funds (I-4; 06 §2.4). Spec: 06 §2.4; 08 §1, §2.3; 11 §5.1, §6.7; 12 §1, §4.5, §11. Cards M1-26-e, M1-34, M2-18a–d, M3-4c.
