# D-159: One relay link per computer: the first AgentLink program shares its relay connections with the others

- **Status:** Decided (owner, 21 Nov 2026: option C, an elected shared link inside an AgentLink program, built right after 0.5.17); linkability mitigation, rollout and caps decided (owner, 21 Nov 2026)
- **Date:** 2026-11-21
- **Specs:** 04, 07, 08, 11
- **Index:** [all decisions](README.md)

## Decision

**One relay link per computer (RELAY-SHARED-CONN, after 0.5.17; amends D-156 (7) for the availability check, see the amendment in [D-156](D-156.md)).** **Decided by Tali in chat, 21 Nov 2026** (option C of three). Today every AgentLink program on a computer (each AI app's `agentlink mcp` and the desktop app's host) opens its own connection to every relay, and the availability check and the server test each open one more. Some relays accept only about 2 connections from one address (RELAY-PER-IP-LIMIT, measured 21 Nov 2026) and turn the rest away. Options assessed: (A) route through the desktop host (nothing is shared when only AI apps run, as in the classroom path); (B) a separate, detached per-user relay daemon (survives AI apps closing, but a detached process per OS, version skew between `npx` versions and one more thing to update, stop and explain); (C) an **elected in-process shared link** (chosen).

(1) **Election.** On each computer, each AgentLink program (Node: the MCP process, the CLI's long-running commands and the desktop host) tries to bind a per-user local endpoint. Binding is the election, exclusive by nature: the first to bind is the **shared link** for that user and holds one connection per relay; the others connect to it as clients and carry their relay frames over that local channel. The cloud agent, the owner console and the browser are unchanged (one Durable Object, one pool; browsers cannot bind). (2) **Keys never move.** Each program keeps its own `RelayPool`, `KeyStore`, `mayAuthenticate` (07 §4.3), signature checks and size limits. Only already-encrypted gift wraps, already-signed events (envelopes and NIP-42 AUTH events), subscription filters and relay URLs cross the channel; never a key, seed, plaintext, file key, OAuth token, storage link or owner secret (I-1, I-2). The seam is `RelayConnector` (07 §4.2): a client's connector returns a virtual socket that carries frames to the shared link. (3) **The shared link only multiplexes.** It rewrites each client's subscription ids (`c<n>:<id>`), routes `EVENT`, `EOSE` and `CLOSED` by subscription id and `OK` by event id to the client that sent it, gives every client on a relay that relay's `AUTH` challenge (each client signs its own AUTH, or none when `mayAuthenticate` says no), and passes `NOTICE` to the clients of that relay. It opens a relay only when a client asks for it, never chooses relays itself, and never parses beyond the frame head. (4) **Local channel authentication (04 §4 "Local relay link").** Unix socket `~/.agentlink/run/relay.sock` in a `0700` directory owned by the user, checked before connect and after bind; Windows named pipe `\\.\pipe\agentlink-relay-<id>` (from a hash of the home folder). Every connection proves knowledge of a 32-byte token in `~/.agentlink/run/relay-link.json` (`0600`) in both directions before any relay frame is read; a wrong proof closes the channel at once. Same-user programs are trusted by design (04 §2.5); this keeps other OS users out. (5) **Not an open proxy.** The shared link re-checks every relay URL with the relay URL rule and the connect-time address check (04 §4; 07 §4.2), opens `wss://` relays only, caps relays per client and connections in total, and offers no other kind of connection. (6) **Untrusted both ways (I-5); counts only in logs (I-7).** Clients verify every event as today; a hostile shared link can only drop or delay, like a hostile relay. No frame, subscription id, event id, URL or token is logged. (7) **Fallback.** The channel's handshake carries protocol `v: 1` and the CLI version. A version mismatch, a failed bind and connect, a failed proof, a stalled channel (past the relay connect timeout) or any other channel failure makes the program use its own pool, which is today's behaviour. Older AgentLink versions keep their own pools and coexist. (8) **Hand-over.** When the shared link's program exits, its clients see the channel close and re-race after a random 0–500 ms; the new winner binds, the others reconnect, and each pool's existing reconnect and sync from its cursor restore subscriptions; the outbox retries anything unacknowledged. The desktop host, when it starts, may ask an MCP winner to hand over (the APP-CONTINUITY yield pattern), so the long-lived process usually holds the link. (9) **Availability check and server test (amends D-156 (7)).** With a shared link, the availability check runs in a machine-wide **check lane** on the shared link: at most one login-free check connection per relay at a time, never the publishing connection, several event ids batched in one `ids` read, closed when its queue is empty, each answer verified by the client that asked. Peak per relay: 2 connections (shared plus check). A refused or silent check stays "Sent, availability unknown", as today. The server test (07 §4.3) uses the same lane and reports whether the shared link is on. Without a shared link: today's behaviour. (10) **Privacy (04 §7).** IDs on one computer now share a connection to a relay, so the relay can link them (they already share an IP address); content stays end-to-end encrypted. (11) **Rollout.** The shared link ships behind the switch `AGENTLINK_SHARED_RELAYS` for one release: off by default in the first release, on by default in the next, unless the owner decides otherwise; `AGENTLINK_SHARED_RELAYS=0` stays as a support switch after that. `agentlink doctor` shows "Shared server connection: on, {n} programs" or "off" (11 §5.15). No data migration. (12) **Out of scope:** a detached relay daemon (option B), sharing across OS users, sharing for the cloud agent, and any proxy or non-relay connection. Mechanics: 07 §4.2 "One relay link per computer" and the availability check; 04 §4 "Local relay link" and §7; 08 §1; 11 §5.15.

**Class and review.** S2 (local IPC, network egress, the AUTH signing path): `RED (expected):` commit first, an independent review of each lane's diff and a Fable 5.2 audit of the channel authentication, the Windows pipe, the SSRF re-checks and the key boundary. Card RELAY-SHARED-CONN, lanes L1 to L5 (`project/process/backlog.md`).

**Acceptance tests (RED first).**

1. Two clients, one relay: exactly one upstream connection.
2. Subscription id rewrite: client A never receives B's `EVENT` or `EOSE`.
3. `OK` is routed only to the client that sent the event.
4. The `AUTH` challenge reaches both clients; each signs with its own key; a client whose `mayAuthenticate` is false sends no AUTH.
5. A wrong or missing token proof closes the channel before any relay frame is read.
6. A socket path owned by another user, or a run directory that is not `0700`, is refused and the program uses its own pool.
7. The winner exits: a new winner within 2 s, subscriptions restored, no message lost (outbox retry).
8. A version mismatch makes the program use its own pool.
9. A disallowed URL or a private address asked for by a client is refused.
10. A frame over `MAX_FRAME_BYTES` is dropped and counted.
11. Check lane: at most one check connection per relay; a refused check ends "availability unknown".
12. No channel frame content appears in any log (I-7 log scan).
13. Windows named pipe in CI, token proof required.
14. The desktop host takes over from an MCP winner.

## Owner decisions (21 Nov 2026)

Decided by Tali in chat, 21 Nov 2026, for these points:

1. **Linkability accepted, with mitigations.** A relay can see several IDs on one connection; this is documented plainly (04 §7). Mitigation: the check lane never puts event ids of different IDs or clients into one read, only ids of the same client; and anyone can turn the shared connection off (`AGENTLINK_SHARED_RELAYS=0`, and later a setting) to keep separate connections.
2. **Rollout.** Off by default in the first release (0.5.18), on by default in the following release, with the off switch kept.
3. **Caps accepted.** 32 clients per link, 64 relays per client, 64 shared upstream connections, 64 ids per check read.
