# @4thtech-io/crypto

## 0.4.4

### Patch Changes

- 6d5b6aa: U3-e: remove an agent from the app (D-138, 08 §1, 04 §2.5). `POST /api/ui/agents/remove {name, typedLabel, anyway?}` is a new named route kind `remove`: it is refused with `in_use` while any process has the agent open (the shared folder lock), checks the typed label, and with one owner gesture always signs `agent.revoke {reason: "retired"}` for the agent, records it in the owner's revoked list (`~/.agentlink/revoked/<agentId>.json`, re-verified as the signed object), marks the agent `removing`, tells its contacts with owner-signed `revoke` envelopes (bounded wait; `undeliverable` asks before going on), erases its keys through the new KeyStore erase API (`KeyEraseControl` in `@4thtech-io/crypto`, keychain and file backends in `@4thtech-io/node`; never an owner item) and deletes its folder, inside the exclusive folder lock. `backup restore` refuses an agent that is in the revoked list.

## 0.4.0

### Minor Changes

- 662785b: M1-PAY-CONFIRM-a: confirming paid actions with the computer's own verification (04 §2.5.3, D-132). Core builds the confirmation statement and the challenge from stored data (`buildPayConfirmFlow`, `payConfirmChallenge`, `spendingChanges`) and refuses a paid item in `approval.decideBatch` (`paid_item_in_batch`). The local approval server adds `POST /api/ui/pay-confirm/begin` and `/finish`: user verification required, single use, bound to the page session, 120 s; the passkey's own signature is verified with the credential key kept at registration (crypto `verifyWebauthnSignature`, ES256 and EdDSA); the backup code keeps the three-tries rule. Approving a paid proof or changing a spending limit through an ordinary owner route now answers `confirm_required`; `agentlink approve` with no ID lists a paid request but sends it to `approve <id>` on its own.

## 0.2.0

### Minor Changes

- cb4a63a: Owner approvals, policies and revocations, envelopes, agent cards and proof packs are now checked from the exact text received: text that repeats a field name or spells one with an escape sequence is refused as malformed before the signature is checked (M1-1h-b, D-128). New in `@4thtech-io/crypto`: `parseReceivedJson`, `parseEnvelopeText` and the `plainMemberNames` option of `parseJson`.
- 3a3837b: `KeyStore.signTransaction` signs one direct-mode transaction with the agent's EVM key, on the launch testnets only: EIP-1559, to the AgentLink Notary, fee vault or an offered fee token, with a direct-mode call (`notarizeDirect`, `notarizeBatch`, `acknowledge`, `acknowledgeBatch`, `deposit`, `withdraw` to the agent's own address, `approve` of the vault), bounded value, calldata, gas and fees. Everything else is refused with `transaction_refused` before any key is read. The keychain KeyStore implements it. `@4thtech-io/chain` adds `keyStoreDirectSigner`, `createDirectMode` (testnets of the KeyStore allowlist only), the typed `buildWithdraw` and `sendWithdraw`, and the ChainError code `signing_refused`.
- 0ece43e: The recovery kit format `ALKK` v1 (04 §2.3.3, D-115; M1-9i-b): `sealRecoveryKit` and `openRecoveryKit` in `@4thtech-io/crypto/keystore`, `readRecoveryKitHeader` and the kit constants in the main entry, with the `recovery-kit` vector suite. The STREAM body of `ALF1` is now shared with the kit (no change to `ALF1` output).
- c6aa21f: `credentialDigest` and `credentialDigestOfItem` (04 §2.5.1 `storage.set`; M1-9i-b2) and the `StorageCredential` types in the main entry; `encodeStorageCredentialItem` and `parseStorageCredentialItem` for the `s3:<id>` item (04 §2.2) in `@4thtech-io/crypto/keystore`. The owner-flow control types `KeyExportControl`, `KeyImportControl` and `StorageCredentialControl` (with `DisplayCode`, `RecoveryKitImport` and the `item_exists` KeyStore error code) for the backends of M1-9i-c. The `recovery-kit` vector suite is now version 2 with the `credentialDigest` cases.
- 9dbaa44: EIP-3009: `verifyTokenDomain(expected, reading)` checks a token's EIP-712 domain as read from chain (EIP-5267 `eip712Domain()`, or `name()`, `version()` and `DOMAIN_SEPARATOR()` recomputed and compared) against the configured chain ID and token address, and refuses a mismatch with the new code `token_domain_mismatch`; `tokenDomainSeparator(domain)` and the pinned `RECEIVE_WITH_AUTHORIZATION_TYPE_HASH` are exported. `parseReceiveWithAuthorization` now refuses an authorization whose `validBefore` is not after `validAfter`. New `eip3009` vector suite.

## 0.1.2

### Patch Changes

- dd9650b: M1-1g-e: `KeyStore.signDropRequest(request, createdAt)` signs one encrypted-drop request with the agent's separate drop key at the current epoch and returns the `Authorization` header (07 §5.4). It is the `DropSigner` the drop adapter takes. The KeyStore fixes the event kind (27235) and the `domain` tag, signs only POST and DELETE to an https URL in serialised form over the drop's signed JSON body with `createdAt` equal to its `ts`, and refuses anything else with one fixed error before reading any key. Implemented by `MemoryKeyStore` and the keychain KeyStore (and its facade). `dropRequestSnapshot` and `DROP_REQUEST_REFUSED` are in the main entry; the raw-key `signDropRequest` is in the restricted `@4thtech-io/crypto/keystore` entry.
- 4d7d3e4: M1-1g-f: `KeyStore.signDropRequest(request, createdAt, options?)` takes an optional `{epoch}` for a DELETE, so an object uploaded under an older key epoch stays deletable after a rotation (04 §2.1). It is accepted only with DELETE and never above the current epoch (`epoch_unavailable`); a POST with an epoch or a malformed epoch gets the same fixed refusal, and every check runs before a key is read. Implemented by `MemoryKeyStore` and the keychain KeyStore (and its facade). `dropRequestEpoch` joins `dropRequestSnapshot` in the main entry.
- 2e6b70e: M1-4d-d-b: the agent card's proof of possession (04 §2.9, D-102). `TAGS.cardPop` (`agentlink/card-pop/v1`), `verifyCardPop`, `verifyCardPossession` and `cardPopSnapshot` are in the crypto main entry; the raw-key `signCardPop` is in the restricted `@4thtech-io/crypto/keystore` entry. `KeyStore.signCardPop(card)` signs only the store's own card at its current key epoch and refuses anything else with one fixed error; implemented by `MemoryKeyStore` and the keychain KeyStore (and its facade). The `handshake` and `handshake-ack` bodies take an optional `cardPop`, and `card-update` optional `cardAgentSig` and `cardPop`, together or not at all. The core makes `cardPop` with every own card (init, so also `owner add-agent`, and rotation once the KeyStore is at the new epoch; a card stored before this change gets one on first use), sends it in `handshake` and `handshake-ack`, verifies a received pair in `handshake`, `handshake-ack` and `card-update` (a present signature that does not verify drops the whole body), and stores a contact's verified pair. `proofSigner(from)` returns the signer block with the pair for the upcoming `exportProofPack` (M1-7g); the core does not yet send `card-update` itself. `verifyProofPack` uses the crypto check instead of its own composition (no behaviour change).

## 0.1.0

### Minor Changes

- 0baa0a5: Add `senderCode(from)` and the frozen tag `TAGS.senderCode` (`agentlink/sender-code/v1`): the 04 §2.9 sender code of an unknown sender (D-72), the tagged hash over the 32 raw bytes of its envelope `from` key, shown with `formatFingerprint(…, 'short')` as in "unknown sender · 2B9E·04D1". Any other length is refused. Display only: it tells senders apart and authenticates nothing.
- 7121fa2: Add the crypto base layer: strict canonical encodings (hex, `0x` hex, base64url without padding, decimal uint256, UTF-8), SHA-256, keccak-256 and BIP-340 tagged hashes, RFC 8785 JSON canonicalisation with a strict parser, secure random bytes and a best-effort wipe helper; anything not in its exact canonical form is rejected.
- 2172526: Add key derivation and public identities: HKDF-SHA256 and the exact 04 §2.1 derivation of the evm, nostr, enc and drop keys (secp256k1 rejection loop, the EVM key only at epoch 0), the agent ID as a lowercase `0x` address with an EIP-55 display form, the X25519 key and its `kid`, a public identity bundle that never carries the drop key, BIP-340 sign and verify helpers, and owner and agent fingerprints with their display forms. Functions that take a master seed or a secret key are exported only from the restricted subpath `@agentlink/crypto/keystore`; the main entry keeps public keys, verification and fingerprints.
- 9c27388: Add envelope encryption: the CEK wrap with RFC 9180 HPKE (mode Base, DHKEM(X25519, HKDF-SHA256), HKDF-SHA256, AES-256-GCM via `@hpke/core`) with info `agentlink/v1/cek` and the raw envelope ID, an empty AAD and an explicit all-zero shared-secret check in both directions; the payload AEAD (AES-256-GCM, random 12-byte IV, AAD = sha256(JCS(header))); a strict v1 envelope parser with the 04 §3.1.1 limits (1 to 8 recipients with distinct `kid`s, `aead.ct` at most 17 152 bytes, checked on its base64url length before decoding; `MAX_RECIPIENTS`, `AEAD_CT_MAX_LENGTH`, `AEAD_CT_MAX_ENCODED_LENGTH`); `envelopeHash`; and the envelope signature input and verification under the `agentlink/envelope/v1` tag. `unwrapCek(secretKey, wrapped, envelopeId)` (it builds the HPKE info itself and takes no caller-supplied info) and `signEnvelopeHash` (it applies the envelope tag itself) are exported only from `@agentlink/crypto/keystore`. New dependency: `@hpke/core` 1.9.0.
- 32b70f5: Add EIP-712 typed-data hashing, canonical secp256k1 ECDSA signatures (`0x` r‖s‖v, low `s`, v 27 or 28; every other form is refused) and the AgentCard: its type under the chain-agnostic domain, a strict parser for its JSON form, `sha256(JCS(card))`, and verification of `cardSig` and the mandatory `cardAgentSig`. The signing functions (`signDigestEcdsa`, `signTypedData`, `signAgentCard`) are in the restricted `@agentlink/crypto/keystore` subpath. `parseJson` gains an `integersOnly` option that refuses `1.0`, `1e3`, `-0` and unsafe integers on the token text.
- cb7c956: Add the owner passphrase wrap and file KeyStore formats, the pairing proof and the safety code: Argon2id (RFC 9106) and the 04 §2.8 `password()` normalisation for generated codes and chosen passphrases, generated 120-bit codes, `ALKS` v1 seal and open (with the in-memory kek check for writes) and `ALKO` v1 owner seed seal and open (local storage only), all in `@agentlink/crypto/keystore`; and, in the main entry, HMAC-SHA256, `proofKey` and the pairing proof, `codeCommit` and its constant-time reveal check, and the 12-digit safety code with its `pairingDigest`, computed only after the revealed nonce opens the commitment.
- fecd9a3: Add owner-only key rotation. `@agentlink/crypto` adds the `KeyEpochControl` interface, a management surface kept apart from the agent's `KeyStore`, so the agent path cannot move the key epoch. `previewEpoch(n + 1)` returns the next epoch's public keys without advancing; until the advance, signing and decryption at that epoch stay unavailable. `advanceEpoch(expected, ownerSession)` is a compare-and-set: it needs a live owner session, and it fails with the new `epoch_conflict` code, changing nothing, unless the store is at `expected`. Older epochs still decrypt. The control is a separate object that the agent KeyStore cannot reach, and it accepts only sessions its paired owner store issued; the test double makes it with `MemoryOwnerKeyStore.epochControl(keyStore)`. In `@agentlink/core`, `identity.rotate` takes the control from the owner flow. It signs the next card, stores it as pending (new `identity.pending_card_json` column), advances the KeyStore, and then commits the new epoch. When the client opens, an owner-signed pending card for exactly the KeyStore's keys finishes an interrupted rotation, unless it has expired or its advance failed. Without one, the agent refuses to send until the owner rotates again.
- 4287032: Add the key interfaces of G-2 (04 §3.1.1) as types in the main entry, so transport and core can name them: `EnvelopeKeys` (`signEnvelopeHash`, `signNostr`, `nip44Encrypt`, `nip44Decrypt`, `unwrapCek`), implemented by `KeyStore` (which adds `getPublicBundle` and `sign712`) and by `OwnerSession` (which adds `signOwnerAction` and `sign712`). No method returns a private key or a seed, no method signs an untagged digest, there is no `hpkeOpen`, and only the decrypting methods and `getPublicBundle` take a key epoch. Owner signatures exist only on a short-lived session from `OwnerKeyStore.unlock(presence)`; it expires on a monotonic clock, is wiped on lock, signs only seal and AUTH Nostr events, and has epoch 0 only, and `lock()` cancels an unlock in flight. Add NIP-44 v2 through `@noble` with strict size, version, base64, MAC and padding checks, Nostr event ids and verification, and a NIP-59 gift wrap whose ephemeral key never leaves the package. `unwrapCek` opens one recipient entry through M1-1c's CEK unwrap with the key of the requested epoch (an owner session: the owner enc key). `MemoryKeyStore` and `MemoryOwnerKeyStore` (not for production) live in the package's one test seam, which is never built or exported, and the NIP-44 functions that take a secret or conversation key are exported only from `@agentlink/crypto/keystore`.
- 1feb21c: **Breaking (unreleased envelope format): key commitment and CEK-derived wraps (G-46, D-66).** The payload AEAD no longer uses the content key (CEK) as its key. `encKey` (`agentlink/v1/payload-key`) and a 32-byte key commitment `kc` (`agentlink/v1/payload-commit`) are derived from the CEK with HKDF-SHA256, and `aead` is now exactly `{alg: "A256GCM-KC", iv, kc, ct}`. The parser and `@agentlink/types`' `aeadSchema` refuse the earlier `A256GCM` form and any `kc` that is not exactly 32 bytes. `decryptPayload` compares `kc` in constant time before AES-GCM and reports a mismatch as the same `open_failed` as a failed tag. The new `checkKeyCommitment(envelope, cek)` lets the core tell the two apart. `wrapCek` is now deterministic: each entry's ephemeral X25519 key is derived from the CEK, the envelope id and the recipient key (`agentlink/v1/cek-eph`) and passed to `@hpke/core` as an imported key pair, never through `DeriveKeyPair`. The new `checkWrap(pk, id, cek, entry)` recomputes one entry from a public key and the CEK and compares it byte for byte. Derived keys are wiped after use. New exports: `checkWrap`, `checkKeyCommitment`, `KEY_COMMITMENT_LENGTH`, `PAYLOAD_KEY_LABEL`, `PAYLOAD_COMMIT_LABEL` and `CEK_EPH_LABEL`. The worst-case envelope grows from 24 509 to 24 563 bytes, still under the 24 576-byte limit.
- 39b1d8c: Add the `terms` schema of 04 §3.4 with the D-74 canonical form: every key always present (`price: null` when none), `parties` in ascending byte order, the character rule on a pinned UCD 15.0.0 table (`refusedCategory15`; Cc, Cf, Zl, Zp, Co, Cs and Cn refused, and NFC) with the Unicode 15 runtime probe (`isTermsRuntimeSupported`, `UNSUPPORTED_RUNTIME`), the D-74 size limits (`TERMS_LIMITS`), currencies by grammar or `USDC`/`USDT`/`XDAI`, and a checked `note`. `TermsInput` (`termsInputSchema`, `parseTermsInput`, `termsInputJsonSchema`, `termsFromInput`) and the pure negotiation-chain reducer (`receiveTerms`, `recordSentTerms`, `nextTermsLink`, `checkSendAccept`, `negotiationKey`, `EMPTY_NEGOTIATION`). In `@agentlink/crypto`: `termsHash` (sha256 of the JCS form, bare hex) and `verifyTermsHash`. **BREAKING:** `offer`, `accept` and `reject` bodies and the commitment approval context now require strict canonical `terms`, and the terms tools' approval `args.terms` must be a strict `TermsInput`; the body `note` is at most 500 code points of canonical text; `hasControlOrFormat` (summaries, `nextStep`) now uses the UCD 15.0.0 table; `isUtcTimestamp` moved from the proof module to the encodings module (same export name).
- e02996f: Add the agent's local store on SQLite: every table of the store schema, with its keys, unique constraints, value types and row limits enforced by SQLite itself, forward-only migrations (a store written by a newer version is refused, never downgraded), WAL mode and write transactions that several processes can share for one agent, and an inter-process lock for longer critical sections. Sensitive columns are encrypted at rest with AES-256-GCM under the agent's store key from the keychain, bound to their table, column and row, and keyed digests use an index key derived from the store key. `@agentlink/crypto/keystore` gains the store column cipher.
