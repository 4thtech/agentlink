# M1-22 e2e: J8 negotiate and agree over Talk

- **Date:** 2026-10-16
- **Task:** M1-22 (S1)
- **Spec:** D-31, D-32, D-55; 02 F-22, F-61, F-62, J8; 06 §2.2a, §3 (`commitments`), §4, §9; 04 §2.5, §3.4, §3.4.2; invariants I-4, I-5
- **Code:** `e2e/test/negotiate-and-agree.test.ts` (deterministic), steps L13 to L20 of `e2e/llm/llm-run.test.ts` (LLM), helpers in `e2e/test/support.ts`

## 1. Purpose

These tests show that two agents can negotiate terms over Talk and agree, that the owner's approval cannot be bypassed by the agent, and that the terms text stays untrusted on the way:

- A binding `accept` leaves an agent only after the owner's signed approval, or inside the owner's signed auto-accept limit (D-31). Each owner is asked once per agreement (D-55).
- Both sides end with the same terms hash.
- Terms written by the counterparty reach the reading agent wrapped as untrusted content (06 §4, I-5) and never reach a summary, `nextStep`, error, tool description or log.

Proof of agreement (notarized terms, the `ACCEPTED` receipt, the exported pack) is M1-13c (M1b) and is not tested here.

## 2. Setup

The harness of M1-13a (see that report, section 2): one process per agent running the built `agentlink mcp`, the real OS keychain and SQLite store, four local strfry relays, the test owner (`MemoryOwnerKeyStore`) behind the CLI's own `agentlink approve <id>` handler. Four agents, two processes at a time (Alice and Bob first, then Carol and Dave, as each process polls the keychain every second): Alice and Bob (default policy), Carol and Dave (Dave's owner has signed a policy that auto-accepts purchases from Carol up to 100 USD). The deterministic variant has a scripted MCP client in place of the model.

What leaves an agent is observed three ways: its own store (sent `accept` envelopes), the tool results, and the relays (the count of events on the four relays; only gift wraps leave the machines, so the count is the traffic). "Nothing leaves" means the count is the same before and after a call, each read once the relays have been quiet for two reads 2 s apart.

## 3. Scenarios

### 3.1 Deterministic (`e2e/test/negotiate-and-agree.test.ts`, 5 tests, runs on every pull request)

| # | Test | What it asserts |
|---|---|---|
| 1 | propose, counter, accept | No MCP tool decides an approval or changes the policy. A proposes (no approval). B reads the offer wrapped (hostile closing tag escaped, one closing tag per message). B counters (version 2, new hash). A reads the counter (same hash). A accepts: `pending_approval`, nothing sent (store and relays). A retry before the decision (still `pending_approval`, same `approvalId`) and a forged `approvalId` (refused) send nothing and open no second request. The owner approves (sends nothing by itself). The retry sends exactly one `accept` (relays grow). A second retry: `APPROVAL_USED`, nothing sent. B reads the accept: version 2, the same terms hash. Approval count: A one, B none |
| 2 | reject | B rejects with a hostile note: free, no approval, one `reject` sent; A reads it wrapped with the offer's hash |
| 3 | versions together, void | A sends version 1 and revises it to version 2 back to back. B receives both and lists both with the right hashes (M1-32-b order independence). Accepting version 1: `TERMS_SUPERSEDED`, nothing sent. Accepting version 2: one approval, owner approves. A sends version 3 before B uses it. B's retry: `TERMS_SUPERSEDED`, nothing leaves B; a repeat is refused too. Version 3 needs its own approval and then sends one `accept` with version 3's hash; A reads it |
| 4 | owner-signed limit | Dave accepts a 50 USD purchase from Carol with no approval and no owner request, once (asking again sends nothing); Carol reads the accept with the same hash. A 500 USD purchase and a sale of 50 USD both give `pending_approval` and send nothing; two requests are open |
| 5 | audit | No hostile text in any tool result other than the inbox; none in the tool list. Every event on the relays is a gift wrap (kind 1059) and holds no canary. The canary scan of every log and result file finds nothing |

Canaries: the owners' seeds and codes (all files and relays) and a random token in the hostile terms (anywhere except the wrapped inbox result).

AGENTLINK_REQUIRE_E2E=1 pnpm --filter @agentlink/e2e test:e2e

## 6. Known limits

- Asking again for the same answer without the `approvalId` opens a new owner request and voids the pending one (04 §3.4.2, one scope per answer): the owner sees only the latest, but it is a second request. The e2e does not do this inside the one-approval-per-agreement count.
- The MCP tool layer does not yet pass `clientRequestId` to the core terms flow (`apps/cli/src/tools/propose-terms.ts` and `respond-to-terms.ts` ignore it), although the core honours it since M1-32-b. A repeated `agentlink_propose_terms` with the same `clientRequestId` therefore still sends a second offer. The e2e asserts the replay protection that exists at the tool layer (the used `approvalId`, `APPROVAL_USED`); a `clientRequestId` repeat check is left until the tool layer passes the key through.
- The owner's `deny` path is covered by the unit tests of M1-9q, not here: the e2e owner helper approves only.
- "Nothing leaves" is observed by event count: it proves no event was published, not what an event held (gift wraps are ciphertext).
