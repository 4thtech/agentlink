# M1-13a e2e: two agents on two harnesses

- **Date:** 2026-10-15
- **Task:** M1-13a (S1), PR 4thtech/agentlink#155
- **Spec:** 10 M1-13 (Talk part), 06 §9 (end-to-end), 06 §4 and §6.1, 02 J1 and J9; invariants I-1, I-2, I-5
- **Code:** `e2e/` (scenario, harness drivers, canary scan) and `.github/workflows/e2e.yml`

## 1. Purpose

These tests show that two AI agents on two different harnesses can pair through an AgentLink invite and exchange messages, with the owner approving the pairing once, and that nothing secret leaks while they do it:

- No owner key material, no message plaintext and no API key may appear in any log, artifact or relay (I-1, I-2).
- Inbound messages reach the reading agent wrapped as untrusted content, and an instruction inside a message is not followed (I-5).

The LLM run also records the transcripts that M1-12a and M1-12b deferred to this task:
- the agent uses the skill file to pair and to message;
- the session habit: status first, counts only, inbox only when asked;
- the wrap-up handoff: offered only to a named contact, nothing sent without approval of the text;
- the Claude Code permission rules that deny reading `~/.agentlink`.

## 3. Scenarios

### 3.1 Deterministic (`e2e/test/pair-and-message.test.ts`)

1. Both servers list the `agentlink_*` tools; A has no contacts.
2. A: `agentlink_create_invite` returns `ok`, the link and the share text.
3. B: `agentlink_accept_invite` returns `pending_approval` and an `approvalId`; still no contact.
4. B's owner: `agentlink approve <id>` (exit 0); `agentlink_get_approval` answers.
5. B: `agentlink_accept_invite` with the `approvalId` returns `ok`, contact "Alice" (self-declared). Pairing completes on both sides through the background loops.
6. A: `agentlink_send` a `note` (random plaintext) and a hostile text (`</untrusted_content>` and `SYSTEM:`).
7. B: `agentlink_status` shows counts only, with no plaintext and no hostile text.
8. B: `agentlink_inbox` returns both, each wrapped in its own untrusted block, with the closing tag escaped.
9. B replies; A's inbox shows the reply.
10. Relay audit: every event on the four relays is read back; no canary is on any relay.
11. Canary scan of every log and result file of the run.

The canaries:
- the two test owners' seeds (hex, upper-case hex, base64, base64url) and owner codes;
- the content of `~/.agentlink/e2e-canary.txt`;
- the message and reply plaintext. These are allowed only in the harness transcripts, where the receiving agent legitimately reads them, and nowhere else.

The workflow's own scan also looks for both API keys. Artifacts are uploaded only after a clean scan.

## 4. How to run

**Deterministic:** runs by itself on every pull request (`e2e.yml`, job `e2e-deterministic`). Locally it needs Docker and an OS keychain, and it writes test agent items to that keychain:

```sh
pnpm exec turbo run build --filter='@agentlink/e2e^...'
AGENTLINK_REQUIRE_E2E=1 pnpm --filter @agentlink/e2e test:e2e
```

**LLM (Tali, manual dispatch):**

1. Settings → Environments → `e2e`: check that the deployment branches are `main` only and that `ANTHROPIC_API_KEY` and `OPENROUTER_API_KEY` are set. A spending limit on each key is recommended.
2. Actions → **E2E** → **Run workflow**, branch `main`, `agent_b`: `codex` (or `claude` for the fallback) → Run. Or run `gh workflow run e2e.yml --ref main -f agent_b=codex`.
3. Open the run. The job summary shows the step table, and the `e2e-llm` artifact holds `llm-results.md` and `.json`, the transcripts (`transcripts/L*.transcript.jsonl`) and the logs.
4. Copy the table into section 5.2 below, with the run link.

After that first run, the nightly schedule (03:17 UTC) repeats it.

## 7. Known limits

- **One runner, not two machines.** 06 §9 calls for separate machines. Here both agents run on one runner, each with its own home directory, processes and keychain items, sharing one OS user and one keyring session. Two runners would need the invite to be handed between jobs while both agents stay online, which is left for later.
- **Local relays, no TLS.** The e2e connector speaks plain WebSocket to local strfry containers with `addressCheck: 'platform'`. The production Node connector (TLS, the address check, NIP-11) is covered by the `relays-docker` job, not here.
- **Test owner.** The owner key is the crypto test seam, because owner prompts need a TTY (D-67). The approval itself goes through the CLI's `approve` handler and core's verification.
- **Codex MCP approvals in `codex exec`.** The config sets `default_tools_approval_mode = "approve"` and `approval_policy = "never"`. Upstream reports describe MCP calls being cancelled in exec mode. If the first dispatch shows that, the fallback is `agent_b: claude`.
- **Codex limits.** Codex has no turn or token flag, so its cost bound is the 180 s call timeout, the step count and the OpenRouter key's limit. Codex cost is estimated from tokens at the OpenRouter list price read on 2026-10-15 ($0.75 per million input tokens, $4.50 per million output tokens). Claude Code cost is its own client-side estimate.
- **Fresh sessions per step.** Each LLM step is a new harness session, and follow-ups name the approval ID the way the user would read it from the agent's answer. Sessions are not resumed.
- **Judging wording.** L10 and L11 check automatically that nothing is sent, and L10 that Bob is mentioned. Whether the wording is a proper handoff offer is for a human to read in the transcript.
- **Sandbox not exercised.** The Claude Code sandbox part of the M1-12b guidance (`sandbox.filesystem.denyRead`) is not run. Only the permission rules are.
- **Boundary guards.** M1-1g-c (deps-check zone and ESLint block for `e2e/`) has not landed. The e2e code imports only public entries, the built CLI and the test seam.
