# CI/CD reference

Scope: GitHub Actions workflows and repository hygiene for `4thtech/agentlink` (task M0-2, CI part; continuous delivery per D-25). Security rules come from `AGENTS.md` and `docs/foundation/04-security-and-crypto.md` §7 (supply chain) and §8. The delivery model (staging, production, rollback, `DEPLOY_FREEZE`) is normative in `release-and-deployment.md`; this file is the implementation reference and the owner's setup checklist. The OCC v2 contracts live in a separate private repository with its own CI; nothing in this repository references its contents.

### Required status checks

Add exactly these four to the `main` ruleset: **`ci-gate`**, **`security-gate`**, **`pr-hygiene`**, **`review-gate`**.

`ci-gate` and `security-gate` are aggregator jobs that always run. They fail if any upstream job failed or was cancelled; a skipped job counts as success. That is what keeps the repository green while it is docs-only, and why individual jobs (which come and go) are never listed as required. `pr-hygiene` is skipped on merge-queue runs, which GitHub treats as a pass. `review-gate` checks only `DEPLOY_FREEZE` on merge-queue runs.

### What runs where (CHORE-CI-SPEED-2)

`ci.yml` spends the runner queue by event. Only `ci-gate` is required, and it counts a skipped job as a pass; no required check is ever itself skipped, so each one reports on every non-draft pull request and on `merge_group`.

| Event | `checks` (lint, typecheck, build, unit tests) | Other jobs | Required checks |
|---|---|---|---|
| Pull request, not draft | **Affected packages only**: the packages the change touches, their dependents (transitively), and the packages whose tests read a changed doc, chosen by `tools/ci/select-affected.mjs` in `detect` (step `affected`) and run as one turbo `--filter` per package; `@4thtech-io/tools` is always included | as before (docs-only skips, Ubuntu legs only) | all four report |
| Pull request that touches `.github/`, `tools/`, root config, the lockfile, `test-vectors/` or `packages/types`, `crypto`, `core` | Full suite (these are global triggers; `.github/` and `tools/` are checked before the selector is read, so a broken selector cannot narrow its own change) | as before | all four report |
| Pull request, selector fails or the diff cannot be read | Full suite, with a warning | as before | all four report |
| `merge_group` (the queue) | **Full suite**, always; the selector is never run | full matrix including macOS and Windows | all four report |
| `push` (any branch, `main`) | Full suite, the selector is never run | as in "Where the heavy jobs run" | `ci-gate (push)` is not required |
| Draft pull request | Skipped (CHORE-CI-SPEED-1: `detect` and `context-budget` carry the draft condition, so every heavy job skips with them; `ready_for_review` starts the full suite) | skipped with `detect`; the secret scan, zizmor, `pr-hygiene` and `review-gate` still run | the gates report (skipped upstream counts as a pass) |

A wrong or too-narrow selection can only delay a failure to the queue, never let it reach `main`: the queue repeats the full suite on the merged result. `dependency-review` and `codeql` are not repeated in the queue (they are skipped there); a pull request runs them on its own commits, and a draft runs them when marked ready for review (`ready_for_review`, CHORE-CI-SPEED-1). Selection rules are in the header of `tools/ci/select-affected.mjs`; its tests are `tools/ci/select-affected.test.mjs`.

### Where the heavy jobs run (CHORE-CI-MATRIX-QUEUE-ONLY)

The runner queue on GitHub Free is the scarce resource, so `ci.yml` spends it where it protects `main`. Only the four aggregators above are required, and `ci-gate` counts a skipped job as a pass, so no job needs a placeholder; a skipped job simply reports "skipped".

- **macOS and Windows legs** (`node-os`, `path-guard`, and the `macos-26` and `windows-2025-vs2026` legs of `keychain`) run only on `merge_group` and on `push` to `main`. A pull request and a feature-branch push run the Ubuntu leg of `keychain` and every other Ubuntu job. A PR cannot reach `main` without the full matrix passing in the merge queue, where nothing is weakened.
- **Docs-only changes** skip `vectors`, `keychain`, `path-guard`, `node-os`, `relays-docker`, `storage-minio`, `bundle-check` and `e2e-deterministic`. `detect` decides from the list of changed file names against the pull request base (or the merge group base): the change is docs-only when every file is under `docs/`, `docs-site/`, `knowledge/`, `changelog.d/`, `.changeset/` or is a root `*.md`. An unreadable diff, a push, or any other file runs everything (fail towards running). A merge group with any code change in it runs everything. `checks` (lint, typecheck, build and every unit test on Ubuntu, which includes all the doc-drift tests for the specs, README, docs-site and knowledge), `context-budget`, `changesets`, `pr-hygiene`, `review-gate` and the secret scan still run on every change. `.changeset/config.json` and other non-`.md` files under `.changeset/` count as code; only `.changeset/*.md` counts as docs.
- **Concurrency:** the existing group `ci-<event>-<PR number or ref>` cancels a superseded pull request run (and a feature-branch push run); runs on `main` and in the merge queue are never cancelled.


### Draft pull requests and the stale-PR precheck (CHORE-CI-SPEED-1)

Owner-approved 2026-10-22 after a day of CI starvation and merge-queue ejections ([`LL-17`](../lessons/LL-17-ci-starvation-stale-pr-ejections.md)). Sensitive path (`.github/**`).

**Draft policy.**

- A **draft** pull request skips the full suite. In `ci.yml`, `detect` and `context-budget` carry `if: github.event.pull_request.draft != true`; every other heavy job `needs: detect`, so it skips with it. In `security.yml`, `dependency-review` and `codeql` skip on drafts. The secret scan and `zizmor` stay on (cheap, and they catch what must never be pushed).
- The `ready_for_review` trigger is added to `ci.yml`, `security.yml` and `pr-hygiene.yml` (`review-gate.yml` already had it). Marking a draft ready starts the full suite on the same head, so `ci-gate` and `security-gate` are recomputed before the PR can merge.
- **Required checks still report on drafts.** All four (`ci-gate`, `security-gate`, `pr-hygiene`, `review-gate`) are jobs that always start on a pull request. `ci-gate` and `security-gate` use `if: always()` and count a skipped upstream job as a pass, so on a draft they go green with "skipped" jobs; `pr-hygiene` and `review-gate` run in full on drafts (tiny). No required job is itself skipped, so nothing sits in "expected, waiting". GitHub refuses to merge a draft anyway, and a PR converted back to draft keeps its earlier results until the next push.
- **The merge queue (`merge_group`) always runs the full suite**: `github.event.pull_request` is null there, so the draft condition is true. Nothing that protects `main` is weakened.
- A **branch push** run (`ci-gate (push)`, not required) cannot see the pull request, so it still runs the suite. Builders who want the saving open the PR as a draft and push; the push run remains the pre-review test. Dropping push runs for branches that already have a PR is a possible follow-up, not done here.

**Stale-PR precheck (`stale-precheck` in `ci.yml`, non-draft pull requests, in `ci-gate`'s `needs`).** The pull-request checkout is GitHub's test merge against the base as of the last PR update, so a PR that fell behind `main` looks green for hours and is then ejected from the merge queue. The job checks out the head, fetches the **current** base, and merges it in a throwaway tree (never pushes). It fails in about a minute, with the fix command in the log, on:

1. a merge conflict (lists the conflicted files);
2. `node tools/docs-status/index.mjs --check` failing on the merged tree (generated status files drifted from `docs/status.yaml`);
3. `pnpm install --frozen-lockfile --ignore-scripts --ignore-pnpmfile` failing on the merged tree (stale lockfile).

Fix commands (also printed by the job). Merge, never rebase:

- Conflict: `git fetch origin && git merge origin/main`, resolve, commit, push.
- Generated status files (`README.md`, `docs-site/technical/project/status-and-roadmap.md`, `knowledge/agentlink-overview.md`) are never merged by hand: `git checkout origin/main -- README.md docs-site/technical/project/status-and-roadmap.md knowledge/agentlink-overview.md && node tools/docs-status/index.mjs`. A conflict in the source `docs/status.yaml` is resolved by hand first.
- Lockfile: `git checkout origin/main -- pnpm-lock.yaml && pnpm install --ignore-scripts --ignore-pnpmfile`, then commit `pnpm-lock.yaml`.

Locally, before pushing a long-lived branch: `git fetch origin && git merge origin/main && node tools/docs-status/index.mjs --check && pnpm install --frozen-lockfile --ignore-scripts --ignore-pnpmfile`.

**Owner-level options (recommendations, the owner decides).**

- **Merge queue size and concurrency.** After the flake fixes land (submitter rate-limit clock, e2e keyring, e2e needle, Playwright apt caching and retry), consider raising `max_entries_to_build` above 2 so independent PRs are tested in parallel, and keep `HEADGREEN` grouping. Doing it before the flakes are fixed multiplies reruns.

### Slow mirrors and the e2e keyring (CHORE-CI-HARDEN-1)

- **Playwright install** (CHORE-CI-HARDEN-1, CHORE-CI-PLAYWRIGHT-2). `ci.yml` (`checks`, `vectors`) uses `.github/actions/install-playwright` with the browsers named in the job (`chromium firefox webkit`; both jobs need all three engines). Steps: (1) `actions/cache` (pinned by SHA) on `~/.cache/ms-playwright`, key = OS + exact Playwright version from `package.json` + browser list, no `restore-keys` (a new version or list is always a fresh download; the step fails if the version cannot be resolved); (2) `playwright install <browsers>` without `--with-deps` (a fast no-op on a hit; CDN download, no apt, on a miss; `timeout 300` and one retry); (3) on Linux, `probe.mjs` launches each browser once through Playwright's own API, which validates its host requirements (the same answer the tests would get; any failure counts as missing); (4) only if a library is missing, and only for the browsers the probe reports (`install-deps webkit` today; an unclear probe result keeps the full list) (or the probe fails for any reason): short apt timeouts and `playwright install-deps` (`timeout 300`, one retry after `apt-get update`). The step keeps `timeout-minutes: 12`. The repository has no apt mirror to fall back to. **Cache poisoning:** a pull request run saves only into its own `refs/pull/N/merge` scope, which `main` and the merge queue never read; fork pull requests cannot write to the base repository's caches; the cache holds browser downloads only and nothing from it is trusted as input to a release.
- **Other apt installs** (gnome-keyring and D-Bus in `ci.yml` and `e2e.yml`) use the same retries and timeout options.
- **e2e keyring.** `tools/ci/with-keyring.sh` now supervises the throwaway gnome-keyring: a watchdog starts it again within about 0.2 s of its end on the same passwordless keyring (unless D-Bus already started a replacement), the daemon runs without `G_DEBUG`, and a health probe must pass before the command starts. If the command fails after the daemon ended, the log carries `::error::runner keychain unavailable` so the cause is plain. No test assertion was changed; a failing keychain still fails the job.

`review-gate` and `CODEOWNERS` together are the GitHub-enforced half of `audit-rules.md` §3:

- **CODEOWNERS** lists only the S2 path defaults plus `/.github/`, `/AGENTS.md`, `/CLAUDE.md`, `/.claude/` and the supply-chain files that can execute code or redirect installs and publishing (`/package.json`, `/pnpm-workspace.yaml`, and `.npmrc` and `.pnpmfile.*` at any depth), each owned by `@talirezun @denisjazbec`. `review-gate` classifies the same files as S1. "Require review from Code Owners" stays **on** (D-51): S2 and code-owned paths need an approval from a code owner who is not the PR author. Under D-51 (simplified) code-owner review is OFF, so CODEOWNERS only requests reviews and notifies; S2 and sensitive-path PRs wait for Tali's "merge" in chat; Denis's approval is optional and also counts (`audit-rules.md` §3).

- It reads the four PR template sections **Security class**, **Independent review**, **Threat note** and **Tests-first evidence**, using the same parser as `pr-hygiene` (`##`/`###` headings, HTML comments and fences ignored). Placeholders (`N/A`, `None`, `TBD`, `-`) count as empty where a section is required.
- **(c) is attested, not proven.** CI checks that a review report is referenced; the report itself is private (`audit-rules.md` §4.5), and the orchestrator attests that the review happened as specified. DECISION NEEDED (owner): run the independent review as a machine job in CI (backlog M0-20). It would need an `ANTHROPIC_API_KEY` secret in an environment unreachable from fork PRs and from non-`main` branches, its output would be advisory, and the PR content it reads is untrusted input (I-5).
- **(d)** requires, for S2, the filled Threat note and Tests-first evidence only (D-51, D-52). The owner removes the former approval check from `review-gate.yml` himself; the owner's go-ahead is the "merge" in chat, recorded in the PR body.
- **Automated PRs (no exemption, one substitution).** A PR is automated only when its **author** (`pull_request.user.login`, set by GitHub) is `renovate[bot]` or `github-actions[bot]` (the Changesets "Version packages" PR). Commit author names, e-mail addresses and the `verified` flag are not consulted: anyone who can push to the branch can forge them. For an automated PR, (c) is satisfied **only** by an APPROVED review by `@talirezun` or `@denisjazbec` on the current head commit (no report ID exists to cite); a new commit, including a bot rebase or "Update branch", invalidates it. - Skeleton-tolerant: it needs nothing but the pull request, checks out nothing and uses no secrets. A docs-only S0 PR passes once its class box is ticked.

### Skeleton tolerance and strict mode

Until the monorepo skeleton exists, `detect` finds no `package.json` + `pnpm-lock.yaml` and every Node job is skipped. It activates by itself when both files appear. Rules once they do:

- `package.json` must pin pnpm with `"packageManager": "pnpm@x.y.z"`, otherwise `detect` fails.
- A missing root script (`lint`, `typecheck`, `build`, `test`, and since M0-9 `vectors:check`) is a warning annotation and the step is skipped.
- **Strict mode:** commit an empty file `.github/ci-strict` and a missing root script (or a `package.json` without a lockfile) becomes a failure. Add it in the same PR that completes the skeleton, so a deleted `test` script can never turn CI silently green. `.github/` is code-owned, so the code owners are notified.

### Contract with the monorepo skeleton

- Root scripts: `lint`, `typecheck`, `build`, `test` (each typically `turbo run <task>`), plus `vectors:check` and `test:e2e` per `docs/process/repo-reference.md`. Turbo dependencies (`typecheck` and `test` after `^build`) belong in `turbo.json`.
- `.nvmrc` is optional; without it CI uses Node 24 (the Active LTS line at the time of writing). The release jobs need npm ≥ 11.21.0 (or ≥ 12.2.0 on npm 12) for OIDC dist-tag rollback; no Node 24 release bundles it yet (Node 24.22.0 ships npm 11.19.1, `nodejs.org/dist/index.json`), so `publish-latest` and `rollback-latest` install exactly npm 11.21.0 from its registry tarball after checking the pinned sha512 (the guard step stays and still fails closed). Remove that step once a Node 24 release bundles npm ≥ 11.21.0 and the pin moves there.
- `playwright` (or `@playwright/test`) must be a root devDependency if the vectors run in a browser; `detect` reads the root `package.json`, not the lockfile (lesson LL-07), and CI runs the `install-playwright` action (browsers from cache or CDN; apt only if a library is missing).
- The root `vectors:check` script calls `node tools/vectors/check.mjs` directly, not through turbo and a package script, so a stubbed or deleted package script cannot turn the job into a no-op (IR-M0-9-1 F01).
- **Install scripts are disabled in CI** (`--ignore-scripts`). A package that needs a native build needs an explicit allowlist: in `ci.yml` pass `rebuild: <package>` to the setup step (a comment shows where). `better-sqlite3` in `packages/node` (from 13.0) ships prebuilt binaries for every platform in its package and has no install script, so it needs none (M1-8b). Do not remove `--ignore-scripts`.
- `pnpm-workspace.yaml`: set pnpm's own `minimumReleaseAge` so Renovate's lockfile maintenance respects the same cooldown as `renovate.json` (check the unit in the pnpm docs).
- `e2e` (`pnpm test:e2e`): since M1-13a, `.github/workflows/e2e.yml` runs the deterministic variant (called from `ci.yml`, part of `ci-gate`, OPS-CI-6) on every code-changing PR and the LLM variant by manual dispatch in environment `e2e`; the nightly two-machine test (OPS-CI-7) is its own workflow (see the workflow table).
- Every published package: `publishConfig.access = "public"` and no `publishConfig.registry`, a correct `repository` field (needed for provenance), no `postinstall` scripts. `.npmrc` sets no registry and no credentials. The release jobs refuse to publish otherwise, because the OIDC token would follow a foreign registry.
- `@4thtech-io/agentlink --version` prints the version (the release smoke tests check it).
- npm channels: prereleases on `next` are made in Changesets pre mode (`changeset pre enter next`); `changeset pre exit` prepares the stable release for `latest` (`release-and-deployment.md` §4.1).

## Security properties of these workflows

- Top-level `permissions: {}`; each job requests only what it needs. Write permissions exist only in `version` (contents, pull-requests), `publish-next` and `publish-latest` (contents, id-token), `rollback-latest` (id-token) and `codeql` (security-events). `record` and `ci-green` read Actions data (who approved; the CI result of the commit being released).
- No `pull_request_target`. No event data interpolated into `run:` scripts or into `github-script` source; values reach scripts through `env:` or the event payload object, and attacker-controlled strings are logged only as JSON strings.
- One secret: `DEPLOY_FREEZE_TOKEN`, only in environment `deploy-freeze` (deployment branch `main`), used only by the `freeze` job of `release.yml` and by `deploy-freeze.yml` to set `DEPLOY_FREEZE`. Future Cloudflare tokens live only in environments `staging` and `production` (`release-and-deployment.md` §6). No PR workflow can reach any secret.
- `actions/checkout` always with `persist-credentials: false`.
- `pnpm install --frozen-lockfile --ignore-scripts --ignore-pnpmfile` everywhere (the composite action). `--ignore-scripts` alone does not stop pnpm from running a repository `.pnpmfile.*`, and both publish jobs run the install while holding `id-token: write`. The project uses no pnpmfile; the action's first step also fails the job if a `.pnpmfile.*` exists, or `pnpmfile` or `configDependencies` appears in `.npmrc`, `pnpm-workspace.yaml` or `package.json` (newer pnpm releases load the pnpmfile for more commands than `install`). `.pnpmfile.*`, `.npmrc`, `pnpm-workspace.yaml` and the root `package.json` are S1 and code-owned. The pnpm store cache is off in every release job.
- The post-publish health checks in `release.yml` run `npm install --ignore-scripts` of the exact `name@version` just published, in an empty scratch directory, only to feed `npm audit signatures`; zizmor's `adhoc-packages` finding is ignored inline on those two steps for that reason (no manifest or lockfile can exist for a version published a minute earlier). Both publish jobs also refuse a project `.npmrc` `tag=` line and any `publishConfig.tag`, besides registry and credential overrides.
- Build code never runs in a job holding `id-token: write` (Changesets pack/publish split), and no job holding it runs package code: post-publish health checks read the registry only, and the CLI smoke tests run in jobs without credentials.
- `timeout-minutes` on every job (the two jobs that call the reusable `secret-scan.yml` cannot set one; the job inside it has 15 minutes); PR runs cancel superseded runs; release jobs never cancel in flight.
- npm publishing uses trusted publishing (OIDC) and provenance, bound to GitHub Environments that only `main` can enter. There is no `NPM_TOKEN` and none should be added.
- Every publish or deploy job is skipped while `DEPLOY_FREEZE` is `true` and re-checks it when it starts.
- Dependency licenses: only an allowlist of permissive licenses passes (`0BSD`, `Apache-2.0`, `BlueOak-1.0.0`, `BSD-2-Clause`, `BSD-3-Clause`, `CC0-1.0`, `CC-BY-3.0`, `CC-BY-4.0`, `ISC`, `MIT`, `MIT-0`, `MPL-2.0`, `Python-2.0`, `Unlicense`, `Zlib`). AGPL, GPL, LGPL, SSPL, BUSL and unknown licenses fail. The action's `deny-licenses` option is deprecated, hence an allowlist. The repository's own licence is MIT (D-12).

## The sync branch

`sync` is an orphan branch (no shared history with `main`) that holds coordination markdown only (`board.md` and per-person files). It is pushed to directly, with no pull requests, so it is deliberately outside the review rules of `main`. Safeguards:

- `ci.yml`, `pr-hygiene.yml` and `review-gate.yml` do not run for it: `ci.yml` ignores pushes to `sync` (`branches-ignore`), the other two run only on pull requests, and all three ignore pull requests into `sync`.
- **Secret scan on every push.** GitHub runs a push-triggered workflow from the workflow files *in the pushed branch*, so a workflow on `main` can never fire for pushes to `sync`. The branch therefore carries one small stub, `.github/workflows/secret-scan.yml`, that calls the reviewed reusable workflow on `main`. The stub is the only non-markdown file on `sync`:

  ```yaml
  name: Secret scan (sync)
  on:
    push:
      branches: [sync]
  permissions: {}
  concurrency:
    group: secret-scan-sync
    cancel-in-progress: true
  jobs:
    secret-scan:
      name: secret-scan
      permissions:
        contents: read
      uses: 4thtech/agentlink/.github/workflows/secret-scan.yml@<FULL-COMMIT-SHA-OF-main>
  ```

  Replace the placeholder with a full 40-character commit SHA of `main` that contains `secret-scan.yml` (`git rev-parse origin/main`). A full SHA (not `@main`) keeps the stub compatible with the repository's SHA-pinning setting. Re-pin it whenever `secret-scan.yml` **or `.gitleaks.toml`** changes on `main` (for example a gitleaks upgrade or a config change): the reusable workflow always loads `.gitleaks.toml` from `main`, so a stale pin runs old workflow logic against the current config and can fail every `sync` push. Procedure: take the current `origin/main` SHA, replace the SHA in the stub's `uses:` line on `sync`, push (`sync-protocol.md`).
- **Pin guard (OPS-CI-4).** The `sync-pin` job in `security.yml` runs `tools/sync-pin-check` on pushes to `main` and weekly (not on pull requests, so a PR that changes the scan is never blocked by a re-pin that can only follow its merge). It fetches `origin/sync`, reads the stub and fails unless the pinned SHA equals, or is a descendant of, the last `main` commit that changed `.github/workflows/secret-scan.yml` or `.gitleaks.toml`. A missing `sync` branch or stub passes with a notice. It is part of `security-gate`; read-only token, no secrets.
- **Weekly backstop.** `security.yml` re-scans the `sync` branch every week using the definition on `main`, so a missing or altered stub is noticed within a week (a missing branch is a no-op). The reusable workflow always takes `.gitleaks.toml` from `main`, so `sync` is scanned with the same allowlist as everything else.
- GitHub push protection and secret scanning (checklist section 1) also apply to pushes to `sync`.
- Nobody reviews content on `sync`; keep secrets, keys, seeds, plaintext and presigned URLs out of it, as everywhere else.
