# D-154: Choose folders in Finder or Explorer, and change the Inbox folder (FILES-FOLDER-PICKER, release 0.5.8)

- **Status:** Proposed, owner confirms at merge (the owner's wish, 14 Nov 2026: pick in Finder for Send and Inbox)
- **Date:** 2026-11-14
- **Specs:** 04, 08, 11
- **Index:** [all decisions](README.md)

## Decision

**Choose folders in Finder or Explorer, and change the Inbox folder (FILES-FOLDER-PICKER, release 0.5.8).** Owner, 14 Nov 2026: "users should be able to click and then select via Finder. It's hard to copy and paste paths", for the Send folders and the Inbox, built "as an industry standard". (1) **One folder row everywhere** (Settings › Files, the Files step, Home's Files panel; D-116 tokens and components): folder icon, the folder's name, the full path under it (cut in the middle, the whole path as its title and read out), a chip, **Show in Finder/Explorer**, **Remove** where allowed; **Add folder…** for another Send folder and **Change…** on the Inbox. After a choice the row shows the folder at once as pending ("Not saved yet"), then the existing confirm (every warning ticked, D-119; passkey or master code), then a success line; a refusal is said in plain words next to the row. (2) **Desktop app: the native dialog.** The window gets exactly one preload (sandboxed, context-isolated) exposing only `chooseFolder({purpose, current?})`; it calls the main process only on a fresh user activation, one dialog at a time. The main process answers only the main window's top frame on the locked origin while a session page is shown, opens `dialog.showOpenDialog` (`openDirectory`, `createDirectory`) modal to the window, preselected at the current folder, and answers ONE absolute path or nothing. Not reachable from the core, MCP or any other process. (3) **Browser:** no fake dialog (a browser never gives a page a path): the click opens an inline path field with an example, paste help and the tip that the AgentLink app can pick in Finder or Explorer. (4) **The picker grants nothing.** A picked path is only text: the server reviews it exactly as a typed one. Send folders: the 04 §4 / D-99 checks, and now also never the Inbox folder, inside it or around it (04 §4.1 "a received file never becomes sendable"). (5) **The Inbox folder changes the same safe way** (04 §4.1 already allowed it "in Settings with a `policy.set` behind presence"; there was no UI): `GET /api/ui/files/inbox/review?set=&version=` checks the 04 §4 / D-99 rules plus: the folder itself not a link, owned by this OS user, on macOS and Linux not writable by group or others, not an OS or app folder (the app's data folders are inside `~/.agentlink`, `~/Library` or `AppData`), not a Send folder, inside or around one, writable, and not the Inbox already; core prepares `policy.set {files: {inboxFolder: <realpath>}}` (warning `folder_changed`); `POST /api/ui/files/inbox` (`presence: true`) signs exactly that body once after checking the folder again. Files already saved stay where they are; new files go to the new folder (every save resolves the rules in force and checks the folder again); Show in Finder follows the rules. Received files are still never opened (I-5). No MCP tool reaches any of it (I-4). Spec: 04 §4.1 "The folder"; 08 §1 "Choose another folder"; 11 §5.7. Card: FILES-FOLDER-PICKER (S2). Numbering: integration may renumber. Invariants I-1 to I-10 unchanged.
