# D-139: Short invite links: the invite is encrypted on the drop, and the link carries only a secret

- **Status:** Decided (owner, 29 Oct 2026); (7), the link shape in (2), the download limit in (4) and the fallback in (6) decided (owner, 29 Oct 2026); the other details of (2)–(6) proposed (owner confirms at merge)
- **Date:** 2026-10-29
- **Specs:** 04, 06, 07, 08, 11
- **Index:** [all decisions](README.md)

## Decision

**Short invite links: the invite is encrypted on the drop, and the link carries only a secret (amends D-69 and D-48).** **Decided by Tali in chat, 2026-10-29** (orchestrator Decision 41, option 1, after the owner's test of 0.4.4: invite links were far too long because they carry the whole signed card). (1) *Decided:* the full invite is encrypted on the user's side and stored on the encrypted drop (D-48); the link carries only the drop ID and the decryption key in the URL fragment (about 40 to 60 characters); the invite works once and expires with the invite (7 days); zero access holds: the drop only ever holds ciphertext, and the key is never sent to any 4thTech service or logged; wave 4 (0.4.6), with a Fable audit. *Orchestrator wording, proposed, owner confirms at merge:* (2) **link format 2** `https://<invite-host>/i#2.<43 characters>`: one 32-byte link secret from which HKDF derives both the 16-byte drop `lookupId` and the AES-256-GCM key, so the drop's ID reveals nothing about the key; (3) invite object `ALI1` v1 (AAD binds it to its `lookupId`; plaintext padded to 1 KiB; at most 17 441 bytes); the inviter never stores the link secret, deletes the object on completion, cancel or expiry, and single use is still enforced by the pairing protocol at the inviter; (4) drop endpoints `POST /v1/invite` (signed by the drop key), unauthenticated `GET /v1/i/{lookupId}` and signed `DELETE /v1/i/{lookupId}`, with per-key upload limits, per-IP and global fetch limits, an invite download limit of 8 (a denial bound, not a security boundary) and one uniform `404`; (5) the fetch URL is built from the configured drop host, never from the link, under the 04 §4 SSRF rules with no redirects; the invite page's CSP allows `connect-src` to the drop host only; (6) `agentlink_create_invite`'s `openWorldHint` becomes `true` when short invites ship, changed in the 06 §2.0 table and the code registry together in the W4-SHORT-INVITE build (the table describes what ships; a drift test ties it to the code); format 1 (D-69) links stay accepted everywhere; creation falls back to a format 1 link when the drop is unavailable; releases before this one refuse a format 2 link. **Threat note (author):** the invite JSON and the pairing protocol are unchanged, so an attacker with the link gains exactly what a format 1 link gives (answer once, first come first served; the safety code detects a swap); an attacker with the ID only, or with drop access, can deny (delete, burn the download limit) but not read or substitute the invite. **New residual:** the drop sees the IPs that uploaded and fetched one invite, so it can tell that two network addresses paired; with format 1 links no 4thTech service saw anything at pairing. (7) **Decided by Tali in chat, 2026-10-29** (orchestrator Decision 44), resolving the open questions: **Q-139-1** the invite download limit is 8 (a denial bound, not a security boundary); **Q-139-2** when the drop is unavailable at creation, AgentLink falls back automatically to the long (format 1) link for the same invite; **Q-139-3** the pairing-metadata residual is accepted, and the long link stays available under Advanced in the app and with `agentlink invite --long` for users who do not want the drop to see that metadata; **Q-139-4** D-129 is amended with a narrow carve-out: invite objects may be used by every user, files on the drop stay internal-testers-only until counsel signs off (superseded: **Decided by Tali in chat, 2026-11-13: files on the drop are open to all early users**; see D-129); the link shape `i#2.<43 characters>` of (2) is kept. Spec: 04 §3.6, §3.6.2, §4, §7; 06 §2 (the `agentlink_create_invite` annotation), §2.1 (both invite tools), §8; 07 §3, §5.4; 08 §1, §4; 11 §6.1. Card: W4-SHORT-INVITE. Invariants I-1 to I-10 unchanged.
