# D-74: `terms` canonical form and negotiation chain made exact

- **Status:** Proposed (owner confirms at merge)
- **Date:** not recorded
- **Specs:** 04, 06, 12
- **Index:** [all decisions](README.md)

## Decision

**`terms` canonical form and negotiation chain made exact (the M1-21 vector generator's open questions, 4thtech/agentlink#98 Q1–Q18).** The independent M1-21 vector generator listed 18 places where 04 §3.4 and 06 §2.2a left `terms` underspecified, two of them (Q3, Q4) changing `termsHash`. Each gets one rule, chosen for safety, strictness, determinism across runtimes and simplicity, in 04 §3.4 ("Canonical-form and chain clarifications") and 06 §2.2a ("TermsInput rules"). **Hash-affecting:** (1) every key of `terms` and of the body is always present; `price` is `null` when there is none (the generator assumed it absent), `deadlines` `[]`, `plaintextSha256` and `note` `null`; an explicit `null` in `TermsInput` is refused (Q3). (2) `parties` are two distinct agent IDs in ascending byte order, refused otherwise, so both sides write the same array whoever sends (the generator accepted any order and wrote own-first) (Q4). **Acceptance only:** `version` 1 exactly when `previousTermsHash` is `null`, a schema rule (the generator made it a chain refusal) (Q11). **Characters:** every string in `terms` and a non-null `note` is NFC and has no code point whose UCD **15.0.0** General_Category is Cc (DEL included), Cf, Zl, Zp (U+2028, U+2029, as for `approval-request.summary`), Co, Cs or Cn (unassigned, noncharacters included); the table is pinned and shipped, not read from the runtime, generated from UCD 15.0.0 `DerivedGeneralCategory.txt` with its SHA-256 pinned and a CI drift check, and also serves `approval-request.summary`; the core probes at load that the runtime implements Unicode 15.0 or later and otherwise refuses all terms with `UNSUPPORTED_RUNTIME` (Q5, Q6, Q7, Q18; IR-D-74-1 F02). Accepting unassigned code points was rejected: a later Unicode version can assign one with a decomposition or a non-zero combining class, and NFC would then differ between runtimes. **Limits:** `subject` 1–200 code points; 1–10 deliverables, ids `^[A-Za-z0-9_-]{1,16}$`, descriptions 1–160 code points; 0–10 deadlines; amounts at most 18 + 6 digits; `note` `null` or 1–500 code points; no empty strings. The largest body is 12 083 bytes as JCS, under 12 255, so a terms payload without files always fits the 17 136-byte payload limit (§3.1.1), which is the binding limit (Q1, Q10). **Other:** the currency is the grammar `^[A-Z]{3}$` or exactly the D-46 / 12 §3.1 fee tokens `USDC`, `USDT` or `XDAI`; auto-accept compares only `USD` and those tokens with USD limits, and needs `price` not `null` (Q2; IR-D-74-1 F05, F06); real dates, no leap second (Q8); deadline refs name a deliverable and are unique (Q9); `TermsInput.validUntil` only in the strict `…Z` form, after now, default now + 604 800 (Q12); an answer names its offer by `replyTo` and copies its terms exactly, and a path-(b) `reject` names the sender's own offer (Q13; IR-D-74-1 F04); terms are valid at t ≤ `validUntil`, a received answer judged by its signed `createdAt`, the receiver's clock only for its own actions (Q14; IR-D-74-1 F03); only the accepted version is locked, n + 1 may follow (Q15); a duplicate envelope is dropped before the chain rules and rule 1 compares by `envelopeHash` (Q16); after a conflict each side may send one resend for that version whose `replyTo` names the other side's conflicting envelope, and any later envelope for it without that link is refused, so both delivery orders converge (Q17; IR-D-74-1 F01). The vectors of #98 and the M1-21 implementation follow these rules; a vector built on a different assumption is regenerated. Moving to a later Unicode version or adding a token symbol is a spec change. Reviewed in IR-D-74-1 (PASS WITH FINDINGS); its findings are applied
