## Decision

**Requests from unknown senders: accept, ignore and block, and refused-row retention (IR-M1-7e-1 F01).** **Fix direction approved by Tali in chat, 2026-10-15**, after the independent review IR-M1-7e-1 of 4thtech/agentlink#95 (M1-7e) found that 11 and the M1-7e card offered "accept / ignore / block" for a request while 04 §2.9 allows a contact only through a completed pairing and nothing defined accept or block, and that `refused` rows from unknown keys counted toward the requests-queue limits with nothing removing them, so a flood of refusals from fresh keys filled the queue for good (F01, Medium). (1) **Accept** marks the request readable: it stays inside the untrusted block (I-5, 06 §4), and the agent offers the user an invite. It never creates a contact row; a contact still comes only from a completed pairing (04 §2.9). (2) **Block** drops the key's envelopes at 04 §3.1.1 step 5 and purges the key's stored request and refused rows. (3) **Ignore** removes the request and also the key's refused rows. (4) **Refused rows from unknown keys expire**, so the owner always has a remedy. **Derived (author; proposed, owner confirms at merge):** *check against the specs:* a request carries no card, so there is no `agentEnc` to address an envelope to (04 §3.2) and AgentLink cannot send the invite to the key; the agent offers `agentlink_create_invite` for the user to share through a channel they trust (04 §2.9, 06 §2.1); accept applies to one request row (`envelopes.request_accepted_at`), which keeps counting toward the limits until ignored, and a later envelope from the key is a new request; *block:* a `blocked_keys` table (07 §3.2), checked at the start of step 5, after the step 4 signature and before any HPKE open, so only an envelope that key signed is dropped and a blocked sender costs no decryption; block also removes the key's held rows; a pairing with a blocked key cannot complete until the owner unblocks it; a `card-update` that makes a blocked key a contact's current key removes the block, and so that it can arrive, an envelope that step 7 would hold for a contact's rotation skips the step 5 drop on its first run (IR-D-72-1 F01; a held envelope from a blocked key is dropped on its re-run when due); Unblock restores nothing; *Ignore all* empties the queue in one step, the remedy against many fresh keys; *retention:* 604 800 s (7 days) from the local `refused_at`, never the sender-chosen `createdAt` (step 9 has not checked it when step 8 refuses), equal to the seen-set's minimum retention: step 9 deduplicates a re-served envelope against the refused row while it exists and against the seen row while a sync can still request it, and a re-count after both are gone gives a sender nothing a fresh key does not (IR-D-72-1 F04); expired rows stop counting at once and are pruned each processing pass; a contact's refused rows are unchanged; *surfaces:* owner surfaces only (local UI, desktop app, `agentlink requests` in an interactive terminal; console from M2), never an MCP tool (I-4); not owner-signed operations (04 §2.5), and in M1 they need no owner presence, an explicit exception in 11 §6.2.1 (IR-D-72-1 F02; revisit for the M2 console), since ignore and block only take away and accept exposes, still wrapped, only what a same-user process can already read from the store (G-1, D-67); an unknown sender is shown as "unknown sender" plus a sender code, the short form of a tagged hash of its key (04 §2.9, 11 §5.2; IR-D-72-1 F07), never as "Contact"; accepted requests reach the agent through `agentlink_inbox` with no sender name and a fixed `nextStep` (06 §2.1); the 11 §6.2.1 and §9 copy; the threat-table row (04 §7); the follow-up card M1-7e-2 (S2)
