## Decision

**Cloud agent for 0.4.0: self-hosted in the user's own Cloudflare account, Claude only, an owner on the Worker's own origin, and one narrow crypto exception for the OAuth library.** **Decided by Tali in chat, 2026-10-25:** the self-hosted cloud agent moves to the front as the headline of 0.4.0, right after 0.3.0 (the usable local app); "All as recommended" for decisions 1 to 8 of the cloud plan; after the CLOUD-0 spikes, "go with your recommendations" for plan changes 1 to 4, and our own stateless MCP handler instead of the deprecated `McpAgent`. *Orchestrator wording of the accepted recommendations, decided:* (1) **Own owner.** The cloud agent has its own owner, created with a passkey on the phone (or any browser). The user pairs it with a desktop agent like any contact and can label it "my other computer" (as D-130 (5)); one owner across devices is later (M2-UX-DEVICE-LINK). (2) **Passkey-only owner presence on the cloud**, with a recovery code shown once, and a typed code as the fallback where the browser has no PRF. (3) **Deploy:** `agentlink cloud deploy`, run from a desktop AI app, is certified first (the agent seed is generated on the user's computer); the Deploy to Cloudflare button follows. 4thTech never runs a page that receives a Cloudflare token. (4) **Plan:** Workers Paid ($5 a month) is the supported Cloudflare plan; the guide says the cost up front (spike S-3: the Free plan's 10 ms CPU per request is too tight for send and sync). (5) **Chat apps, with plan changes 1 and 4: 0.4.0 is Claude only:** claude.ai on the web and the Claude iOS and Android apps (a connector added on the web or desktop appears on the phones; spike S-1). ChatGPT mobile is out of 0.4.0 (developer-mode apps are web only); ChatGPT web comes later, and no ChatGPT Business seat is bought now. (6) **OAuth grants are owner-signed, listable and revocable.** (7) **Template** in a separate public repository `4thtech/agentlink-cloud-agent`, generated one way from `apps/cloud-agent` at a release tag, pinning npm versions that carry provenance. (8) **Versioning:** self-hosting moves from 0.3.0 to 0.4.0 in the docs (`versioning.md` §3, 10, the README roadmap, guide stubs). (9) **Plan change 2:** the button's guide page generates the setup code and the seed wrap key in the browser (Cloudflare cannot generate secrets, spike S-4); they never leave the browser except into the user's own Cloudflare secret prompts. Button users get no automatic updates, so the cloud agent tells them when a newer template release exists ("update available"). (10) **MCP:** no `McpAgent` (deprecated and feature-frozen, spike S-7); a stateless MCP handler (the MCP SDK's web-standard streamable HTTP transport) in front of our own `AgentDO`, which owns the store, alarms and the KeyStore. (11) **Plan change 3, the narrow crypto exception (04 §8 rule 1):** `@cloudflare/workers-oauth-provider` may use the platform's WebCrypto internally, **only inside `apps/cloud-agent`**, which runs only in the user's own Worker, with a Fable audit, and the owner-signed grant list checked on every request. **Exactly what it covers** (the exception itself, its scope to `apps/cloud-agent`, the Fable audit and the per-request check are decided; the version rule, the primitive list, the off-paths and the deps-check zone below are *proposed, owner confirms at merge*): *library:* `@cloudflare/workers-oauth-provider`, an exact pinned version at least two weeks old (1.2.3 today), zero runtime dependencies, published with provenance; *primitives:* `crypto.getRandomValues` (codes, tokens, grant IDs), SHA-256 (stored token hashes, the PKCE S256 check), HMAC-SHA-256 (a per-token key for the grant data), AES-GCM (the grant data at rest in the Worker's KV) and AES-KW (that data key wrapped under the per-token key), all through the platform's WebCrypto, never a primitive of its own; *off:* the library's features that use other primitives or keep consent outside our check, the signed-JWT client and enterprise grant paths (ECDSA P-256 and RSA verification) and its HMAC-signed "remember this approval" cookie, are never configured, and a test fails if they are; *where:* a deps-check zone allows the package in `apps/cloud-agent` only; our own code still calls no primitive (the `crypto.subtle` rule is unchanged) and the cloud agent's keys and messages go through `@4thtech-io/crypto` and `KeyStore` as everywhere; *why:* Claude's connectors need an OAuth 2.1 server (PKCE, client registration, refresh rotation), writing our own would be a custom security protocol (worse for I-8), and the library cannot take our primitives instead. **Why zero access and I-1…I-10 still hold:** the library sees only OAuth data: authorisation codes, access and refresh tokens, client registrations and the grant's data, which holds only the grant ID, client ID and scope. It never sees an agent or owner seed, a wrapped owner blob, an envelope key, a file key or any message or file content (I-1, I-2). It runs in the user's own account, and no token or grant reaches 4thTech (I-3). A token only lets the chat app call the tools within the owner-signed rules; it can never produce a `SignedOwnerAction`, and a grant counts only while an owner-signed authorisation for it exists and is not revoked, checked in `AgentDO` on every request, whatever the library's own token state says (I-4; spike S-1: the library keeps the previous refresh token valid once). Tokens, codes and grant data are never logged (I-7). The primitives are the platform's audited WebCrypto (I-8). I-5, I-6, I-9 and I-10 are unchanged. *Derived details:* (c), (f), (g), (h) and (j) are decided (owner, 2026-10-26); the others stay *proposed, owner confirms at merge:* (a) the owner pages live on the Worker's own origin (`/setup`, the OAuth sign-in page, `/approve/<id>`, `/status`); the owner seed exists only in the browser, for one owner operation per gesture (04 §2.5); the Worker keeps only the `ALKP` and `ALKR` blobs (04 §2.2, §2.5 "Cloud owner presence"); the 4thTech console stays later (plan item 9); (b) the passkey RP ID is the exact Worker host, never the account's `workers.dev` subdomain, preview URLs are off, and changing the host means re-enrolling with the recovery code (spike S-6); (c) **decided (owner, 2026-10-26):** the fallback code for a lost passkey is the recovery code itself (one code to save, `ALKR`, unwrapped with Argon2id in the browser, never in the Worker); (d) the grant is the owner-signed op `connector.authorize` (grant ID, client ID, client name, redirect host, scope, expiry) and its removal `connector.revoke`, both signed on the owner pages only, never by a tool (04 §2.5.1, 06 §1 rule 4); (e) 0.4.0 signs in to OAuth only with the owner passkey (or the fallback code) on the Worker's page; the console-signed challenge and `agentlink cloud login` follow with the console (08 §3.3); (f) **decided (owner, 2026-10-26):** relay sync is alarm-only, every 60 s, with no always-open relay socket (spike S-5); (g) **decided (owner, 2026-10-26):** cloud `agentlink_fetch_file` saves to the user's R2 and returns a link on the Worker's own host that works for 15 minutes; the R2 copy is deleted after 7 days (resolves G-14); (h) **decided (owner, 2026-10-26):** the approval page offers "Open in Safari" or "Open in Chrome" when the chat app's built-in browser has no passkey support (spike S-2); (i) Cloudflare logs, Tail and Logpush are off in the template, as for the drop; (j) **decided (owner, 2026-10-26):** the allowed OAuth redirect hosts are a default list of the chat apps we have tested end to end, which in 0.4.0 is `claude.ai`; every app we test joins the default list (ChatGPT on the web next), and any other host is allowed only under Advanced. The product stays model-agnostic, as the local agent works with every MCP app. **Also decided by the owner in chat, 2026-10-26:** (k) cloud `agentlink_send` with a file path returns `CLOUD_FILES_NOT_YET` in 0.4.0; sending files from the cloud agent comes later (06 §2.3); (l) template updates: the release job pushes a new version to the template repository only after the owner's approval click, with a token scoped to that repository, never automatically (`release-and-deployment.md` §4.8); (m) connector grants: access tokens live 1 h, refresh tokens rotate and live 30 days, and every grant expires after at most 30 days, so the owner signs in again about once a month; this applies to every connecting app (08 §3.3); (n) the rest of the M2 cloud work ships in later 0.x releases, not in 0.4.0 (`versioning.md` §3). **Threat note (author):** new trust: the user's Cloudflare account and whoever can deploy code to it (it can serve a page that captures the owner seed after a gesture, like a compromised console host); Cloudflare as the user's processor; a guessable `workers.dev` name before setup (setup code); OAuth token theft (scope, owner-signed grant, per-request check).
