## 1. Local approval UI (P0)

- Served by the MCP/CLI process on `http://localhost:<random port>`, listening on `127.0.0.1` and `::1` with the same port and on no other interface (D-79; a machine with no IPv6 loopback listens on `127.0.0.1` only). A random **session token** is kept in memory only and included in the URL the process opens (`/?t=…`); it is never written to disk. Reject requests without the token, with a wrong `Host` header, or from other origins (DNS-rebinding protection). Reject any `Host` other than exactly `localhost:<port>` (including `127.0.0.1:<port>`), and any `Origin` other than `http://localhost:<port>`. A POST must carry that Origin.
- The token only grants *viewing*. Every owner operation (approve, policy, folders, storage, backup) additionally requires **owner presence**: a WebAuthn passkey registered for `localhost` (PRF unwraps the owner key) or the owner passphrase. So a shell-capable agent that opens the page still cannot approve (04 §2.5). The passkey is registered on this page with one entry of the owner code, stored as `ALKP` v1 under `owner-passkey`, and checked as in 04 §2.3.1 (M1-8e; proposed, owner confirms at merge).
- **Owner setup on the first-run page (M1-11s-c, D-120 (1); proposed, owner confirms at merge).** While no owner exists anywhere, `/first-run` offers setup: `POST /api/ui/first-run/owner/begin` (empty body) returns the WebAuthn creation values, and `POST /api/ui/first-run/owner/finish` (the creation response) creates the owner with that passkey, a backup owner code returned once for a collapsed "Backup way to approve" display, and the agent's first card, all or nothing (04 §2.2, §2.3.1). Both are `presence: 'setup'` routes behind their own setup gate (session, CSRF, Origin, fetch metadata, octet-stream body, backoff, then "no owner exists"), never the owner-presence gate. Once an owner exists they answer `owner_exists` and the page shows "Approvals are already protected on this computer". A failure answers `failed` with a fixed `reason` (`rolled_back`: nothing kept, start again; `keychain`: items may remain, `agentlink doctor`; `check_failed`; `internal`); `done_unconfirmed` means the owner was kept and its code is shown, but the card could not be confirmed (`agentlink doctor`). After setup the page shows the owner fingerprint, and the CLI logs it in a fixed line; the race this leaves is in 04 §2.5 (G-1).
- **First run v2 (0.3.0; D-130 (1), (2); flow decided by the owner, details proposed, owner confirms at merge; card M1-UX-FIRSTRUN-V2).** The first-run page leads with the passkey on a platform authenticator: the passkey is created with `authenticatorSelection: {authenticatorAttachment: "platform", residentKey: "required", userVerification: "required"}`, the PRF extension and `hints: ["client-device"]`, and the button names the platform ("Use Touch ID", "Use Windows Hello", otherwise "Use a passkey"). Before the gesture the page shows the folders that setup creates (`~/AgentLink/Send`, `~/AgentLink/Inbox`, `~/AgentLink/Proofs`, mode 0700) and that Send will be allowed. The one confirmation then creates the owner, registers the passkey, signs the first card and signs the first policy (the 06 §3 defaults with `files.allowedFolders` = the real path of `~/AgentLink/Send`, which must be a real folder, never a link (at either level), new or empty; anything else is refused before the gesture, as for `policy allow-send-folder`, 06 §8), all or nothing, as one owner flow (04 §2.5; M1-36b-2-b); where PRF comes only from a following `get()`, that second gesture follows in the same flow (M1-11s-c-c). The owner code is then shown once as "Your backup code", in a real `<form>` whose username field is `autocomplete="username"` with the fixed value "AgentLink backup code – <computer name>" and whose code field is `autocomplete="new-password"`, so "Save in my password manager" lets the browser's own save sheet appear; "Copy" is secondary and warns that other apps can read the clipboard; the page continues only after "I saved it". The setup routes never return the code to anything but this page (never to a tool, a log or terminal output). Then the recovery kit (D-120 (2)) and "Ready". If the browser offers no platform passkey with PRF, the page says which browser on this computer works (M1-UX-PRF-MATRIX) and offers to continue with the backup code only. An owner who already has an owner code (0.2.0) enters it once to register the passkey (the bullet above; design adjustment B-9).
- **Confirming paid actions (D-132; decided by the owner, 2026-10-27: confirmed with the computer's own verification; which actions, the backup-code link and the sheet closing itself after Done decided on the same day; ceremony details proposed, owner confirms at merge; card M1-PAY-CONFIRM-b).** A proof approval, verified registration and a change to the spending limits open one confirmation sheet: what it is for, the amount, "Paid from your credits", "Your credits stay yours; 4thTech never holds them." and "Confirm with Touch ID" (or Windows Hello, or your passkey, named as below). The sheet renders only the confirmation statement the server returned and the ceremony requires user verification, bound to that statement (04 §2.5.3). Proofs inside the signed limits stay automatic. Design: `docs/design/b11-local-app.md` §19.
- **Approving with the passkey (D-130 (1)).** On every approval card the main button is "Approve with Touch ID" (or the platform's name, as above); "Use backup code instead" is a secondary link that opens a wide field that accepts paste, with show and hide (card M1-11b-5). Proposed (Q-130-1, 04 §2.5): the backup-code field on approval cards sets `autocomplete="off"`, which asks the browser not to fill in a saved code (browsers may ignore this). A password manager keys the saved code by host, so it may also offer it to a look-alike page on another local port: part of the fake-prompt residual (04 §2.5).
- Opens automatically (or via OS notification) when approval is needed; `agentlink ui` opens it manually. **Home is the landing page (D-138; decided by the owner, 2026-10-29; card U3-a).** `agentlink ui`, a bare `agentlink` in the owner's terminal (06 §8) and the end of first run open Home (with Start here, `docs/design/b11-local-app.md` §27), every time; an approval or a `needs_setup` open still goes to its own page (below).
- **Opened for the owner by the AI (D-130 (3); decided by the owner, details proposed, owner confirms at merge; card M1-UX-OPEN-APP).** An agent-run `agentlink ui` (no TTY or a harness marker) opens the page through the OS opener, as in the owner's terminal, and prints one fixed line built with `cliPrefix()`: that the page opened in the browser, or, when no browser can be opened (SSH, headless), the command to run in the owner's own terminal. It never prints the link. The MCP server opens the approval page on `pending_approval` (06 §2.5) and the Files page on `needs_setup` with code `NO_ALLOWED_FOLDER` (06 §2.3), with no new tool (D-53). The rules are in 04 §2.5 ("What the AI may cause"): OS opener only, no link or secret in a result, no value taken from a URL parameter, only after this agent's own tool call, at most one open per 30 s. On a missing folder the Files page shows a banner with the fixed default only: "Allow ~/AgentLink/Send for sending files?", with one passkey gesture (`policy.set`; card M1-UX-SEND-FOLDER-EXISTING). This replaces M1-11b-9's "run by an agent, it opens nothing".
- Pages: Home (landing page, D-138) · Approvals · Activity · Messages (Inbox and Sent per contact, read-only; D-133) · Contacts · Files (tabs Received · Sent · Send folders; Send folders holds the allowed folders and the inbox folder; D-133) · Storage (optional, Advanced: shows whether files go through the encrypted drop or own storage, with drop usage; own S3-compatible storage is connected in the terminal (`agentlink storage connect`, 06 §8); the page shows its status and a "connect in terminal" step, and tests it, D-48, D-117) · Proofs & credits (balances, agent address QR, top-up options) · Policies · Backup (export behind the owner's passkey; restore is terminal only, D-117 A) · Agents (D-138, below) · AI apps (D-138, below; in the sidebar after Contacts until an AI app is connected, then under Settings) · Advanced (keys fingerprint, relays, RPCs, chains).
- **Messages and Files In/Out (D-133, D-134; decided by the owner, 2026-10-27; route limits and error codes proposed, owner confirms at merge; cards MSG-FILES-IO-a to -h, plan `docs/process/proposals/MSG-FILES-IO.md`).** People see what their AI sent and received without asking it. **Read-only:** the pages never send, reply or change anything; there is no compose box, and the footer says "To reply, ask your AI." **Local only:** the pages show what the local agent already holds in its store (received and sent messages, received and sent files); nothing new is sent to any 4thTech service, the relays, the drop or a chain, and the pages work offline. **Reading in the app does not mark anything read for the AI:** the AI's read state is never changed; the page keeps its own "seen" marker in the browser (per contact, the time of the newest inbound message looked at, never message text), which drives the Messages badge.
  - **Messages** (sidebar, between Activity and Contacts): contacts on the left (unknown senders and removed contacts are not listed; requests stay in Contacts); for the chosen contact, tabs **Inbox** and **Sent**. Inbound text and other people's file names are shown only inside the untrusted-content container as plain text (I-5): no Markdown, HTML, images or previews, and a link is an inert chip showing its domain. Long text is clamped with "Show all"; **Copy text** is allowed. Sent items show their status and receipt. Under the hood: message ID, size and proof status only.
  - **Files** has three tabs, Received first: **Received** (from, when, size, proof, and the name it was saved under in the Inbox folder, labelled "saved as" because the person may have moved or renamed it since), **Sent** (file, to whom, when, status, receipt, expiry) and **Send folders** (today's folder cards). The app never opens a received file.
  - **Routes** (all `GET`, `presence: false`, behind the same session, CSRF, `Host` and fetch-metadata gate as every `/api/ui/` route): `/api/ui/messages`, `/api/ui/messages/:contactId?box=in|out`, `/api/ui/files/received`, `/api/ui/files/sent`. Each item is built from an allowlist: never a file URL, file key, drop link, presigned URL, raw envelope or sealed value. They write nothing to the store. They are not MCP tools, and no MCP tool is added or changed (I-4). Paging: `limit` 1–100 (default 20) and an opaque cursor of at most 256 characters; errors are fixed codes (`not_found`, `bad_request`, `unavailable`) and never carry message text; logs carry counts only (I-7).
  - **Activity pulse** (UX2-f1, b11 §24, UX-WAVE-2 decision 4.1; proposed, owner confirms at merge): `GET /api/ui/messages/pulse`, `presence: false`, behind the same gate, no query parameters. One aggregated read of the local store (both directions, contacts that are not removed, never one read per conversation): `{ now, bucketSeconds: 7200, partial, contacts: [{ contactId, counts, lastAt, activity }] }`. `counts` are twelve two-hour buckets over the last 24 hours, oldest first; `lastAt` is the newest exchange in the window; `activity` is `active_now` (within 5 minutes), `today` (since the local midnight) or `quiet`. A contact not listed is Quiet. **Counts and times only**, from columns the store keeps in clear (07 §3): never message text, a subject, a file name or size, or anything else inbound (I-5). Bounded: core reads at most 10 000 envelopes per direction, the answer lists at most 1 000 contacts (most recent first), and `partial` says when either cap left something out. Messages up to 5 minutes in the future (another agent's clock) count as now; later ones are not counted. Errors: `bad_request`, `not_set_up`, `unavailable`.
  - **Where a fetched file was saved:** the store records the single file name `agentlink_fetch_file` gave the file in the Inbox folder, sealed like the file's name (store schema 6). It is a name, never a path.
  - **Show in Finder** (D-134) for a saved received file needs no owner presence (no Touch ID). The request carries only the item ID; the server opens only the file the store recorded for that item, and only if it is a regular file directly inside the Inbox folder (04 §4 realpath rules), through the OS opener with no shell. It is one fixed local action in its own route kind, a `POST` without presence (with invite create and check since UX2-d1, below); it signs nothing and writes nothing to the store. Every other mutating route stays presence-gated (D-118).
  - **Save a received file (W4-FILES-SAVE, owner test of 0.4.4 B7; proposed, owner confirms at merge).** A file that arrived and is not saved reads "Arrived · not saved" with **Save to Inbox**. Saving needs owner presence (Touch ID or the backup code, the same step as an approval) and signs one local `file.save` (04 §2.5.1); core then saves the file into the Inbox folder with the same fetch as `agentlink_fetch_file` (local decryption, the SSRF-safe download, both hashes, a sanitised name that never overwrites, 04 §4). Route: `POST /api/ui/files/save`, `presence: true`, octet-stream body (the presence), `X-AgentLink-Input` exactly `{"id":"<item ID>"}` (`<envelope ID>.<index>`, index 00 to 15). Never a name, a folder or a path from the page: anything else is `400 bad_request`, checked before presence and again after it; a file already saved is `409 already_saved` before presence. Fixed answers (types `ui-contract/inbox.ts`): `200 {status: "saved"}`; `404 not_found`; `409 too_large`, `integrity_failed`, `expired`, `location_refused`, `policy_denied`, `refused`, `not_set_up`; `502 download_failed`; `503 inbox_unavailable`, `unavailable`. No answer carries the saved name, a folder, a path, a link or an error's text; the page reads the list again for "Saved as". The app still never opens a received file.
  - **Inbox (W4-INBOX, Decision 40, b11 §34.4; proposed, owner confirms at merge).** The home of the wave-4 app. **Needs you** on top: requests waiting for approval, each a card with Approve and Deny and the presence step inline ("Confirm with your passkey" or the backup code), through the existing approval routes (no new way to approve, never without presence; a paid request opens the confirmation sheet, 04 §2.5.3); new messages (this browser's "seen" marker, as on Messages); files that arrived and are not saved, with Save. **All caught up** when nothing waits. **Conversations** per contact below: messages both ways with their files inline (a received file with its state and Save), that contact's approvals as cards beside the thread, and "To reply, ask your AI." Reads are the Messages, Files and Approvals `GET`s above; inbound text and file names only inside the untrusted container (I-5). The shell routes `/inbox` and drops the Approvals, Messages and Files sidebar items (D1).
  - **Message history** is kept as today, for as long as the contact is not removed (D-134). File retention is unchanged (04 §4).
  - **Session residual (D-134):** the documented local-session residual of this page (04 §2.5, D-67) now also covers message text. Accepted for 0.3.x and revisited before M3. The AI gains nothing from it: it already reads the same messages through its own tools.
- **Add contact: invites in the app (UX2-d1; owner decision 1.1, decided by the owner, 2026-10-28; route details proposed, owner confirms at merge; design b11 §21).** Creating an invite needs no owner presence, like `agentlink_create_invite` (04 §3.6 sets no invite policy, so a shell-capable agent gains nothing). It is the fifth named route kind, `presence: 'invite'`, beside setup, pay-confirm and reveal, with two fixed `POST` routes: `/api/ui/invites` (body `{}` or `{"label": "<name>"}`; core `createInvite`; answers `inviteUrl`, `shareText`, the short owner fingerprint and `expiresAt`, as the tool does; at most 10 per 10 minutes per running app, then `429 wait`) and `/api/ui/invites/check` (body `{"invite": "<link>"}`; accept step 1 only, 04 §3.6: the one D-69 codec, schema, expiry, both card signatures and the relay URL rule of 04 §4; stores nothing; answers who it is so the page can ask "Is this who you expected?" before Touch ID). Both sit behind the same session, CSRF, `Host`, `Origin`, fetch-metadata and octet-stream checks as every write, refuse a query, an operation input or a presence header, never open the owner store and sign nothing. **Accepting** (`POST /api/ui/invites/accept`, input `{"invite": "<link>"}`) leads to a new contact, so it is an ordinary owner route behind the presence gate: step 1 again, then `contacts.acceptInvites`; the owner's presence signs one `approval.decide` (approve) for the same approval action the MCP tool and the CLI build (the open request for it, or a new one), core verifies and applies it, uses it once and only then stages the pairing. A `deny` rule or a bad invite signs nothing. Only the canonical link or the bare payload reaches core; any other host, scheme or shape is refused first, and nothing in these routes fetches anything except, for a short link (D-139, 04 §3.6.2; proposed, owner confirms at merge), core's one GET of the invite object from the configured drop host (create uploads it). Under Advanced, the Add contact sheet offers the long link (D-139 (7), decided by the owner, 2026-10-29): `/api/ui/invites` then takes `{"long": true}` (with or without `label`) and creates a format 1 link that uploads nothing to the drop. A short link fits easily within the size bound below; the resolved invite is kept sealed with the open approval, never re-fetched for the accept. The invite link appears only in the create answer to the page: never in a URL of the app, a title, a notification, a toast, Activity, an event, a log or an error (I-7), and never through a 4thTech service. Check and accept share one size bound, the longest link the accept route's input header can carry (about 6 KB; AgentLink's own invites are far smaller): both refuse a longer one with `invalid_invite`, and it is accepted through the AI or `agentlink accept`. The owner sees the same approval summary on every surface (the MCP tool, `agentlink accept` and the app): the name under the name rule, its label and the short owner fingerprint (04 §3.6 Accept step 2). Every other mutating route stays presence-gated (D-118).
- **Agents and AI apps in the app (usability wave 3; D-138, decided by the owner, 2026-10-29; cards U3-a to U3-flow, plan `docs/process/proposals/USABILITY-WAVE-3.md`; owner operations and residuals in 04 §2.5 and §2.5.1, card U3-spec-04; design b11 §28 to §32).** One app serves every agent of the owner on this computer, with **one agent open at a time** (06 §6).
  - **App host.** The `ui` process is the app host: it lists the agents, opens the current one through the same `openAgent` path as every other process, and on a switch closes it and opens the other in the same process, port and session (no new link, no new token). The server reaches agent folders only through an **`AgentDirectory`** seam the CLI passes in (list, read config, write label, mark removing, remove folder), implemented over the CLI's agent-folder code, so the folder and name rules (06 §6, 07 §9.1) stay in one place. The host never takes the publisher lease (06 §6); it reads the lease row to show Running. Which agent opens first: the last used (`~/.agentlink/app.json`, 07 §9.1), else the agent an AI app runs (`default` first), else the first by name; with no agent yet, Welcome (first run v3, below). **With no agent yet (U3-g-b; proposed, owner confirms at merge)** the host starts with no agent open: it serves the app pages, the setup-time reads (`GET /api/ui/first-run`, `/api/ui/apps`, `/api/ui/agents/label-check`, `/api/ui/agents`, `/api/ui/health`) and first run's `begin` and `finish` only; every other route and the approval API answer the fixed `409 no_agent` after every guard. First run's `finish` then creates the first agent in the folder `default` (as `init` names it, D5, so its AI app entry needs no `--agent`; later agents use the label slug), with the label the owner typed ("My agent" when none is given), and opens it in the same host, port and session, raising the generation. An agent folder of any kind (even one marked `removing`) means first run is refused here (`owner_exists`).
  - **Generation.** Each switch increases a generation number held by the host. Every read answer carries the generation and the open agent's label; **every mutating request** (every `POST`, including approvals, policy, folders, invites and the routes below) carries the generation it was built against and is refused with `agent_changed` when it differs. The generation is a page guard, checked twice: when the request arrives, before any presence check, and again right before the server acts. It is never part of a signed object. Every owner statement the page shows before a Touch ID gesture names the agent's label, so a gesture never approves something for an agent the owner is not looking at. An approval page opened by an MCP process (06 §2.5) stays bound to that process's agent; its switcher says "Open the AgentLink app to switch".

The name is checked under the agent-name rule (06 §6) and must be a listed agent that is not `removing`. It closes the open agent and opens that one, writes only `app.json`, and signs nothing.
    - `POST /api/ui/agents` `{label, generation}` (presence; also signs the agent's first `agent.label`): creates a keychain agent whose first card the owner signs (04 §2.8) with its first policy (the 06 §3 defaults, as in first run) and its label (06 §6 label rule, else `label_invalid`); the folder name is a slug of the label under the agent-name rule, made unique with a suffix. The page then offers "Connect an AI app to it?". *From W4-ONE-TOUCH (D-140; decided by the owner, 2026-10-29, Decision 43 W5; route details proposed, owner confirms at merge):* creating an agent is two calls and one gesture. `POST /api/ui/agents/begin` `{label, app?, generation}` (no presence, signs nothing) creates the agent's keys in memory, reserves the folder name, computes the AI app change and its `changeId` for the new `agentId`, and answers the statement and the plan-bound challenge of 04 §2.8 ("Create an agent and connect its AI app with one gesture"); `POST /api/ui/agents` `{nonce, generation}` (presence) then signs the card, the policy, the label and, when `app` was given, the `app.connect`, and writes the entry last. Its fixed answers add `created_not_connected` (the agent was created, the entry was not written: the page offers **Connect**, the ordinary `apps/apply` with its own gesture) and `changed`. The "Connect an AI app to it?" offer remains for an agent created with "Not now".
    - `POST /api/ui/agents/label` `{name, label, generation}` (presence; signs `agent.label`): changes the label only. The folder name, AI app entries and identity stay the same. *From W4-RENAME-REACHES-CONTACTS (D-141; proposed, owner confirms at merge):* when `label` differs from the name in the agent's current card, the same gesture also signs the agent's next card with that name (04 §2.5.1, §2.6); the core then sends the `card-update`s, and the answer adds `contacts` (how many active contacts will be told). A process that has the agent open (an AI app's `agentlink mcp`) picks up the new card when it next sees the stored epoch ahead of its own (`key_epoch_mismatch`, 04 §2.6) and never sends under the old one.

It is also allowed during setup, before an owner exists, behind the same local-origin and page-session guard, with the same entry-only output (below); it writes nothing.
    - `GET /api/ui/apps/preview?app=&agent=` (read): `app` must be an app of the fixed table (06 §7) and `agent` a listed agent under the agent-name rule (06 §6), else `bad_request`. It answers the `agentlink` entry change for that app and agent, and a `changeId`, a digest (through `@4thtech-io/crypto`) over the app, the resolved config path, the old entry, the new entry and the agent. A preview writes nothing.
    - `POST /api/ui/apps/apply` `{changeId, generation}` (presence; signs `app.connect`): recomputes the change, refuses with `changed` when its `changeId` differs, then writes it under the 06 §7 rules. Moving an app from one agent to another is the same step; the page shows both entries ("Claude Code will use Work instead of Personal").
    - `POST /api/ui/apps/disconnect` `{changeId, generation}` (presence; signs `app.disconnect`): removes this agent's entry only, with the same preview and `changeId`.
    - `GET /api/ui/flow?since=<cursor>` (read): the live connections view (b11 §32), polled every 3 s while the page is visible: at most 200 items `{contactId, direction, kind: message|file, state, bytesDone?, bytesTotal?, at}` for the open agent, from columns the store keeps in clear (07 §3); never text, a subject, a file name, a link or an envelope; logs carry counts only (I-7). As built (U3-flow, proposed, owner confirms at merge): the answer is `{now, cursor, items, partial}`; `since` is whole unix seconds, inclusive, the last minute when absent and never older than 24 hours; `cursor` is always a minute ago (so an item stored late with an older time is never skipped; the page keeps the newest per line); an item up to 5 minutes in the future counts as now; `state` is `received` inbound, else `queued`, `sent` or `not_delivered`; at most 200 items and 20 000 bytes, newest first, `partial` when a bound or core's scan cap (200 per direction) left any out. The store keeps no upload byte counts, so `bytesDone`/`bytesTotal` are never sent and the fill is indeterminate; no contact name, envelope ID or hash is sent either.
  - **Signed local owner actions.** Every presence route above signs an owner action, so the D-68 rule that a presence route which signed nothing is refused still holds. `agent.label` `{agent, label}`, `app.connect` `{app, agent, changeId}` and `app.disconnect` `{app, agent, changeId}` are **local owner actions** (04 §2.5.1), where `agent` is the agent's `agentId`: stored and nonce-checked in the agent's store like `contact.check`, with a lifetime of at most 600 s, never sent in an envelope, and verified by the server before it acts. The owner statement names the agent's label and, for `app.connect` and `app.disconnect`, the AI app, for the owner to read; the signed object binds `agent` (the `agentId`) and its nonce, never the label alone, and never the generation (a page guard, above). The label in `config.json` is display only (07 §9.1): it never decides which agent an action applies to.
  - **Entry-only config display.** AI app config files hold other servers' entries and their secrets (API keys). The list, the preview and apply parse the file and show **only the `agentlink` entry**: never context lines, other entries or the whole file, and nothing from the file reaches a log, an error or an answer (I-7). The written entry is fixed (06 §7: `npx -y @4thtech-io/agentlink mcp` plus `--agent <name>`, checked again) and never holds a secret. Claude Desktop is never written while it runs ("Quit Claude Desktop first", re-checked; the app never closes it, 06 §7). An existing `agentlink` entry the app did not write stays a conflict with manual steps. After a write the page says "Restart {app} to finish".
- Approvals and policy changes produce owner-signed actions that the core verifies.
- Same React component library as the console (shared `packages/ui`), bundled into the npm package.
- The local UI is a React app in `apps/local-ui` (Vite, browser-only, uses `packages/ui`), built into static assets that the CLI embeds and serves through this server; `packages/node` carries no React. Owner presence and signing stay on the server and the browser never signs; every mutating route is presence-gated centrally (D-118).
- Known limit: a passkey registered for `localhost` can be requested by any page on any localhost port (04 §2.5). The desktop app (§8, M2) removes this with a native approval window; this page stays for `npx` users.
- **Top-up link (D-111, format decided in D-113, 2026-10-21).** `needs_credits` (06 §2.4), `agentlink_status` `topUpUrl`, `agentlink credits --topup` and the Proofs & credits page all give one link to the pay page (§2.3): `https://{payHost}/#v=1&a=<agent address>&usd=<suggested amount>`. Address and amount sit in the fragment, so they never reach the pay host's server; the link names no network or token (D-40); `usd` is the shortfall rounded up to the first preset and at least the minimum, and is optional; `v=1` versions the format. `{payHost}` comes from the shipped chain config (`PAY_PAGE` in `@4thtech-io/chain`), never from inbound content. **Gated on a live pay page (M1-26-e review):** the config also says whether the page is `live` (default no, until it is deployed); while it is not, no tool or command gives a link, a QR code or opens a browser, and `needs_credits` says adding credits is not available yet. Design: `docs/design/topup-ux.md` §5.

## 2. Owner console (P1, M2)

**Static PWA**, hosted by 4thTech on Cloudflare (and self-hostable). No backend; it talks only to relays, public RPCs, the encrypted drop or the user's storage (for previews) and submitters. Its screens (`packages/ui`) also serve as the desktop app's local dashboard (§8, D-41).

### 2.1 Identity

- **New owner:** passkey creation with PRF → owner seed generated in browser (see 04 §2.2) → encrypted backup published to relays → recovery kit download offered.
- **Existing local owner (CLI-created):** `agentlink owner link` shows a QR / link with a one-time transfer: the CLI encrypts the owner seed to an ephemeral X25519 key generated by the console page (key exchange via QR + 6-digit code shown on both sides). The console then wraps the seed with a new passkey.
- **Sign-in on a new device:** passkey → `user.id` gives owner Nostr pubkey → fetch encrypted backup → PRF unwrap.
- If PRF is unavailable: generated recovery code flow (04 §2.3).

### 2.2 Functions

| Area | Behaviour |
|---|---|
| **Agents** | List owner's agents (from agent cards); add agent (pairs a local or cloud agent to this owner); revoke |
| **Activity** | Subscribe with the owner Nostr key on the relays of all the owner's agents, as their owner-signed cards authenticate them (07 §4.3, G-24; accepted with D-65); decrypt all envelope copies; unified timeline across agents. Reading owner copies, including NIP-42 AUTH, needs an `OwnerSession` opened with presence, and a copy appears on an agent's thread only under the attribution rules of 04 §3.1.1 ("Where the owner shows a copy"). That reading needs presence is a UX trade-off for the owner to confirm (D-39, D-40) |
| **Threads** | Per contact; messages, files (download + decrypt in browser), proof badges and receipts |
| **Approvals** | Approval requests arrive as encrypted `approval-request` envelopes from agents; owner approves/denies; decision returned as an owner-signed `approval` envelope (04 §3.4.1) |
| **Policies** | Edit per-agent policies; sent to the agent as an owner-signed `policy` envelope; agents accept only if signed by the owner key in their agent card (satisfies I-4) |
| **Proofs** | List notarized records, receipts, export proof pack, open verify page |
| **Credits** | Balances per agent and chain; "Add credits" opens the pay page (§2.3) for that agent with the top-up link (§1, D-111): crypto first, the user's own account or an exchange, and card last once live; fee history, including top-ups |
| **Storage** | Optional, advanced: show whether each agent uses the encrypted drop or own storage (D-48); guided own-storage setup for cloud agents |
| **Settings** | Passkeys, recovery kit, relays (the owner's own additions to the bootstrap set, local only and never published, 07 §4.3), RPC overrides, language |

### 2.3 Web security

- Strict CSP: `default-src 'self'`; `script-src 'self'` with SRI; `connect-src 'self' https: wss:` (required because counterparties' storage hosts and relays are arbitrary; content is still end-to-end encrypted); no third-party scripts or analytics; `Trusted Types`.
- The **deposit page** (which may load a wallet connector such as WalletConnect) runs on a **separate origin** (`pay.`) with no access to owner keys; it only receives the agent address.
- **Pay page methods (D-111; direction, owner decides details).** Crypto first: the page works with no card path (decided). Free test credits come first on testnets, then **use crypto you already have**, connecting the user's own account (WalletConnect, EIP-6963 providers), detecting the network from the account's stablecoin balances with the D-40 rule and asking for one confirmation, a transfer of the exact amount to the agent's address that the agent turns into credits gaslessly (M3-4b); and **send from an exchange**, the agent's address with a QR code, the coin and the network named only inside the exchange steps, as information and never a choice (D-117 B), with the $5 minimum (D-117 D) and wrong-network guidance. **Pay by card** comes last, after the legal entity is decided (D-15): a provider's own hosted checkout (no provider script inside `pay.` unless a CSP review accepts it; the provider gets only the agent address and the amount; approach and provider open, M2-18a, M3-4c). Every cost is the user's (12 §1). Progress is read in the browser from public RPC (balance at the agent's address, `creditsOf`); the page stores nothing server-side and offers a payment record built in the browser. Each method states its privacy effect once (D-109, 12 §4.4). Design brief: `docs/design/topup-ux.md`.
- Reproducible build; release artifacts and their hashes published on GitHub; the console shows its build hash in Settings.
- Separate origins: `console.`, `verify.`, `invite.` (or path-based with care).

## 3. Cloud agent template (P1, 0.5.0, D-131)

**Repo:** `apps/cloud-agent` in the monorepo. It is generated one way into the public template repository `4thtech/agentlink-cloud-agent` at a release tag, for the "Deploy to Cloudflare" button (D-131 (7), `release-and-deployment.md` §4.8).

**What 0.5.0 gives the user (D-131).** An always-on agent in the user's **own** Cloudflare account, used from Claude on the web and in the Claude iOS and Android apps: "Send this to Ana's agent" works from a phone. 0.5.0 is Claude only; ChatGPT web comes later and ChatGPT mobile is not supported (D-131 (5)). The supported plan is Workers Paid, $5 a month (D-131 (4)). 4thTech hosts nothing that holds a key (D-37).

### 3.1 Components

- **Worker** (entry), on one host, `https://agentlink.<account>.workers.dev` by default: `/mcp` (streamable HTTP MCP, served directly with no redirect), the OAuth endpoints and metadata, the owner pages (`/setup`, the sign-in page, `/approve/<id>`, `/status`), `/health`. Preview URLs are off, and `/mcp` is never redirected (proposed, owner confirms at merge).
- **AgentDO** (Durable Object, SQLite-backed): exactly one per deployment (`idFromName("agent")`), so it is the single publisher (06 §6; proposed, owner confirms at merge). It holds the store (the local schema, 07 §3), the agent `KeyStore`, the outbox, approvals, the owner-signed grant list (§3.3) and the owner's `ALKP` and `ALKR` blobs (opaque to the Worker). Relay sync runs on alarms only (every 60 s by default, with no always-open relay socket, because outbound sockets keep the object in memory and billed; decided by the owner, 2026-10-26, D-131 (f); spike S-5). The alarm re-arms itself first, is idempotent, keeps a per-relay cursor (cold start reads back at most 48 h) and opens at most 5 relay sockets per run.
- **MCP:** a stateless MCP handler in the Worker (the MCP SDK's web-standard streamable HTTP transport, the same SDK major as the stdio server) that calls the shared tool handlers (`packages/mcp-tools`, 06 §1) against `AgentDO`. Not the Agents SDK `McpAgent`, which is deprecated (D-131 (10)).
- **OAuth:** `@cloudflare/workers-oauth-provider`, inside the narrow crypto exception of D-131 (11) and 04 §8; sign-in needs the owner (§3.3).
- **Storage:** the user's R2 bucket binding, created by the template. Received files are saved there and handed out as a short-lived link (06 §2.3, G-14). Own S3-compatible credentials stay a later option.
- **Logs:** Workers logs, traces, Tail and Logpush are off in the template's Wrangler config, and a deploy check refuses a config that turns one on (I-7, as for the drop, 07 §5.4).

### 3.2 Keys and the owner

- **Agent seed, desktop path (certified first, D-131 (3)).** `npx -y @4thtech-io/agentlink cloud deploy`, which the user's desktop AI app can run, opens Cloudflare's own sign-in in the browser (Wrangler), generates the agent seed **on the user's computer**, sets it with `wrangler secret put AGENT_SEED` in the **user's** account, deploys, and prints the setup link with the setup code in the link's `#` part (never sent to a server; proposed, owner confirms at merge). Wrangler keeps its sign-in on the computer, so the CLI then says to run `wrangler logout` (04 §2.5 "Deploy credentials on the computer"). 4thTech never sees the seed or a Cloudflare token.
- **Agent seed, Deploy-button path.** Cloudflare copies the template into the user's GitHub or GitLab account (the guide says a free account is needed) and asks for two secrets. The guide page generates both in the browser, with copy buttons, and never sends them anywhere (D-131 (9)): `SETUP_CODE` and `SEED_WRAP_KEY`. On the first `/setup`, the Worker generates the agent seed and stores it in `AgentDO` sealed under `SEED_WRAP_KEY` through `@4thtech-io/crypto`. Both stay in the user's account.
- **Owner (D-131 (1), (2)).** The cloud agent has its **own** owner. `/setup` asks for the setup code, then "Protect your agent with Face ID": one passkey gesture creates the owner seed **in the browser**, wraps it under the passkey PRF (`ALKP`, 04 §2.3.1), signs the agent's first card and first rules (06 §3 defaults) and shows the recovery code once (`ALKR`, 04 §2.3.2), with a save step. The Worker receives only the public keys, the signed objects and the two wrapped blobs; it hands the blobs to any browser that asks, which is safe because neither opens without the passkey or the recovery code (04 §2.5). If the owner loses both, nobody can approve for this agent again: the user deploys a new agent and pairs again with each contact. `/setup` then closes for good: it is single use, and refused once an owner exists. Owner presence on the cloud is in 04 §2.5 "Cloud owner presence".
- **Pairing with a desktop agent.** Like any contact; the accept card offers the local label "my other computer" (D-130 (5)). One owner across devices is later (M2-UX-DEVICE-LINK).
- **Host name.** The passkey belongs to the exact Worker host (04 §2.5). Renaming the Worker, changing the account subdomain or moving to a custom domain means enrolling again with the recovery code; the guide says "keep the address" (spike S-6).

### 3.3 OAuth sign-in (Claude connectors; D-131 (6), (11); redirect hosts and grant lifetimes decided by the owner, 2026-10-26, D-131 (j), (m); other details proposed, owner confirms at merge)

1. The user adds `https://<host>/mcp` as a custom connector on claude.ai (Settings → Connectors). It then appears in the Claude iOS and Android apps on the same account; connectors cannot be added on a phone.
2. `/mcp` without a token answers 401 with the protected-resource metadata. Its `resource` is the exact public `/mcp` URL, fixed at deploy time (or pinned at `/setup`), never taken from the request's `Host` header. The authorisation server metadata advertises PKCE `S256`, dynamic client registration and client ID metadata documents (CIMD, with `none` as the token auth method), and the `iss` response parameter. Claude's redirect URI is `https://claude.ai/api/mcp/auth_callback`. The allowed redirect hosts are a default list of the chat apps we have tested end to end (D-131 (j), decided by the owner, 2026-10-26): in 0.5.0 that list is `claude.ai`, and every app we test joins it (ChatGPT on the web next), so the cloud agent stays model-agnostic like the local one. A registration or sign-in for a host outside the default list is refused unless the owner allows that host under Advanced on `/status`. Allowing an extra redirect host is an owner-signed action that needs owner presence (the passkey or the recovery code on `/status`), never available to an AI tool (I-4; 04 §2.5.1; proposed, owner confirms at merge). CIMD fetches use the Workers public-only fetch flag.
3. The sign-in page (design `Cloud-signin`) names the app asking, its redirect host and what it gets: "talk, files and proof within your rules; never your rules or keys". The owner approves with the passkey (or the fallback code); the browser signs `connector.authorize` (04 §2.5.1) for that grant. Registering a client grants nothing without this step, and there is no "remember this approval".
4. **On every `/mcp` request** the handler takes the grant ID and client ID from the library's verified token data and `AgentDO` checks that an owner-signed `connector.authorize` exists for them, with a matching scope, not expired and not revoked. Otherwise it answers 401 (`invalid_token`) and revokes the library's grant too. The scope is checked by our handler (the library does not enforce scopes). Access tokens live 1 h; refresh tokens rotate and live 30 days; every grant (`grantExpiresAt`) expires after at most 30 days, so the owner signs in again about once a month. This applies to every connecting app (D-131 (m), decided by the owner, 2026-10-26).
5. `/status` lists the grants (app name, when added, last used) and removes one with `connector.revoke`, signed on that page. A removed grant fails at its next request, whatever the library's token state is (it keeps the previous refresh token valid once, spike S-1).
6. A token is equivalent to a compromised AI app: it can talk and spend within the signed rules and budget, never sign an owner action (I-4). The 4thTech console's signed challenge and `agentlink cloud login` (a one-time access code from the CLI) come later with the console.

### 3.4 Autonomy

Cloud agents can be **autonomous** (act on inbound messages without a harness, e.g. auto-acknowledge, auto-reply via a configured LLM) only within policy. Default: autonomous actions off; inbound queued for harness or owner. Not in 0.5.0.

### 3.5 Updates, cost and leaving (D-131 (4), (9); template updates decided by the owner, 2026-10-26, D-131 (l); other details proposed, owner confirms at merge)

- **Updates.** Users deploy into their own accounts, so 4thTech cannot update or roll back their agents. A new template version reaches the template repository only after the owner's approval click, never automatically (D-131 (l), `release-and-deployment.md` §4.8). The Worker compares its template version with the latest release tag (a plain public read, nothing about the agent sent) and, when newer, `agentlink_status` says "An update for your cloud agent is available" with the steps ("Sync fork" on GitHub for button users, `agentlink cloud update` from a computer), and `/status` shows the same.
- **Cost.** The guide states Workers Paid ($5 a month) before the deploy. Limits per IP on `/mcp` and the OAuth endpoints and the unknown-sender limits (07 §3.2) keep floods from raising the bill.
- **Leaving (I-10).** `/status` downloads an `ALKK` recovery kit after the owner's gesture (04 §2.3.3); the guide lists the uninstall steps.

A bare payload, another host or scheme, a second `#`, percent-encoding, whitespace or any extra argument is refused with one fixed line, "This isn't a complete AgentLink invite. Open the link again and copy the command.", exit code 2. No part of the argument is ever printed, logged or put into an error (I-5, I-7). `join` never reads the clipboard or standard input, and never fetches anything from the network except, for a short link (D-139, 04 §3.6.2; proposed, owner confirms at merge), one GET of the invite object from the drop host in the shipped config (04 §3.6.2: no redirects, size cap, 10 s); its only other request is the loopback handoff below, which carries the resolved invite in its body.
- **What `join` does.** With no app host running, it starts the app exactly as `agentlink ui` does (§1: loopback only, session token in memory, D-138 opening rules), and that host keeps the checked invite **in memory only** as the *waiting invite* (one per host). While a waiting invite is shown, a handoff of another invite is refused with the fixed code `invite_waiting` (`join` then prints "Finish or close the invite already open in AgentLink, then run the command again."); a waiting invite is replaced only after "Not now" or its expiry.
  - **An app host already running** (proposed, owner confirms at merge): `join` hands the invite over instead of starting a second host. Each running host keeps a **handoff record** `~/.agentlink/app-host.json` (mode 0600, written at start, removed at exit; `{pid, port, handoffToken}`, where `handoffToken` is 32 random bytes and is not the page's session token, which stays in memory only). `join` reads it, checks the pid is alive, and sends **one loopback `POST /api/ui/join/handoff`**, connecting to `127.0.0.1:<port>` (never resolving a name) with exactly `Host: localhost:<port>`, the token in a header, no `Origin`, and the body `{"invite": "<link>"}` (octet-stream, the size bound of `POST /api/ui/invites/check`). The invite travels only in that request body: never in a URL, a query or a header. The route is its own kind, `presence: 'handoff'`: it accepts only that token (compared in constant time), refuses any request with an `Origin`, any `Sec-Fetch-*` header, a cookie or a session, accepts at most one handoff per 5 s (then `429 wait`), runs Accept step 1 again, stores the waiting invite, signs nothing, and then opens the join screen through the OS opener (M1-UX-OPEN-APP rules: one open per 30 s). The token grants nothing else: no read, no other route. A stale record, a dead pid, a refused or failed handoff makes `join` start its own host as above. A local process that can read the record can only set a waiting invite, which still needs the owner's Touch ID to accept.
  - Either way, AgentLink never writes it to disk, `app.json`, `app-host.json`, the store, a URL of the app, a title, a notification, Activity, a log or an error, and it never reaches a 4thTech service.
  - No owner on this computer yet: the app opens Welcome and **first run v3** runs unchanged (§1: pick your AI app; name your agent and Use Touch ID; connect your AI app, or Later). It then ends on **"Accept {name}'s invite?"** instead of Home.
  - Already set up: the app opens on the same screen, for the agent it opens (§1; the generation rule applies).
  - Run by an AI (no TTY or a harness marker): the same, through the OS opener, printing only the fixed M1-UX-OPEN-APP line (§1); where no browser can open, the line says to run the command from the invite page in the person's own terminal. It never prints the invite.
  - `join` never accepts, never signs anything and never writes an AI app config itself.
- **The AI path (D-39).** The sentence makes the person's own AI run `init`, which shows the exact configuration change and applies it only after the person confirms (06 §7), then shows the person the exact `join` command to run in their own terminal (proposed, orchestrator Decision 36: until M1-UX-OPEN-APP, the AI does not run `join` itself). When `init` already set up the agent and connected that AI app, first run v3 keeps the name and Touch ID screen and shows the AI app as connected instead of the connect step. Owner setup, the safety code and the accept all happen in the app, never through the AI. The invite link is in the AI's conversation, as with the D-53 prompt (06 §7.1); the AI never gains an approval from it.
- **Routes** (behind the same session, CSRF, `Host`, `Origin`, fetch-metadata and octet-stream gate as every `/api/ui/` route; fixed error codes; no MCP tool is added or changed, I-4):
  - `GET /api/ui/join` (read; like `GET /api/ui/apps`, also allowed during setup, before an owner exists): `{state: none | waiting | expired | own | already_accepted | connecting | waiting_for_them | connected, inviteId?, inviter?: {name, label, fingerprint}, expiresAt?}`. `inviteId` is the invite's public 16-byte ID (never its `secret`), used only to bind the accept to what the screen shows. `name` is the name-rule output. Never the link, the payload or any other invite field.
  - `POST /api/ui/join/accept {inviteId}` (input in `X-AgentLink-Input`; the generation in `X-AgentLink-Generation`, as every write; U3-invite: a different `inviteId` is refused before the presence gate as well as after it): an ordinary owner route behind the presence gate, refused before an owner exists. The body carries no invite, only the `inviteId` of the invite the screen shows (from `GET /api/ui/join`, which also answers it); when it differs from the waiting invite's, the route answers `invite_changed` and signs nothing. It runs Accept step 1 again on the waiting invite (expiry against the current time), then `contacts.acceptInvites`: the owner's presence signs one `approval.decide` (approve) for the same approval action as `POST /api/ui/invites/accept`, the MCP tool and the CLI build (§1, 06 §7.1), used once; only then is the pairing staged and the waiting invite dropped from memory. A `deny` rule or a failed check signs nothing.
  - `POST /api/ui/join/dismiss {}` ("Not now"; the generation in `X-AgentLink-Generation`): the `invite` route kind (§1), no owner presence, signs nothing; it forgets the waiting invite.
- **Before Touch ID.** The screen reads "Accept {name}'s invite? Check it's {name}: {fingerprint}" (wording confirmed by the owner, Decision 32), where `{fingerprint}` is the short owner fingerprint; it shows the name with its Self-declared label and "For: {agent label}" (04 §3.6 Accept step 2), and the owner statement names the agent's label. The safety code does not exist yet (04 §3.6.1); the screen says "After you connect, compare the safety code with {name}." (wording confirmed by the owner, Decision 32). Once the `handshake-ack` arrives the app shows "Connected with {name}" and the safety-code step (b11 §8 screen 10; "They match" signs `contact.check`), then Home with Messages ready.
- **Expiry, single use, already used.** Expiry is checked on the page, by `join` and again at accept (advisory; the inviter enforces its own, 04 §3.6): "This invite has expired. Ask {name} for a new one." The page and this computer cannot see whether someone else used the invite first (there is no server; only the inviter knows, 04 §3.6 "A second answer"). Locally: when this agent already answered the same `inviteId` (a pending or completed pairing), the state is `already_accepted` ("You already accepted this invite."); the agent's own invite is `own` ("This is your own invite."). After accept the app shows "Waiting for {name}'s agent to answer" and, while it waits and no AI app runs the agent, finishes the pairing itself with short lease-gated passes for the open agent (at most once per 5 s; the same passes follow any pending pairing on either side and, every 15 s while a page is visible, bring in new messages; an AI app's server holding the lease always wins; 06 §6, U3-invite-b, Decision 37; proposed, owner confirms at merge); after 10 minutes with no answer it adds "If nothing happens, the invite may have been used already or {name}'s AI app isn't running. Ask {name} to check, or for a new invite."
- **Residuals (proposed, owner confirms at merge).** The command holds the invite: the person's shell may keep it in its history file, and other accounts on the same computer can see a running process's arguments. npm also writes the full command line to its debug log (`~/.npm/_logs/*-debug-*.log`) on every `npx` run, and the package lands in the npx cache, so the link reaches the disk outside `join`'s control. All of these are local, never a 4thTech service. The command names the package without a pinned version, as the D-53 prompt and `init` do; what `npx` fetches as `latest` is gated by the owner's npm release approval (D-52). The invite works once and expires (default 7 days), and a copy used first by someone else is caught by the safety code and by the inviter's "Someone else also answered your invite" (04 §3.6). No new secret is exposed: the link already travelled over the chat the person used, and its secret is single use, expires and is dead once the pairing completes.
- **Tests (U3-invite).** Crafted fragments containing `'`, `"`, space, line breaks, `;`, `$(…)`, backticks, `%`, `&`, `|`, `^`, `!`, `\`, a second `#`, percent-encoding, a look-alike host and confusable characters yield the damaged state with no command and no sentence; the Copy buttons yield exactly the template plus the canonical link with no line break; `join` refuses each of these argument forms with the fixed line and exit code 2 and prints nothing from the argument; a spy shows `join` makes no network request before the app opens and writes the invite nowhere (file system, store, logs); the M1-19 name test above also covers the new heading.

**Proof-pack links (G-52; decided by the owner in D-71 (6), 15 Oct 2026, on the orchestrator's recommendation).**
- **Format.** A proof pack (07 §8) shared as a link uses the invite's link format (04 §3.6, D-69): `base64url(deflateRaw(utf8(JSON)))` of the pack, in the URL fragment of the verify page, so it never reaches a server. Compressed bytes are never hashed, signed or compared.
- **Decoder.** The verify page decodes it in the browser with the same bounded, strict decoder as the invite (04 §3.6): the input bounded before any parsing, inflation in bounded slices with a running output count and a cap, the stream ending exactly at the end of the input, fatal UTF-8, I-JSON and the strict pack schema. *Derived (proposed; owner confirms at merge):* one generic capped-inflate function in `@4thtech-io/core` serves both, with its caps set per payload type.
- **Pack caps.** The pack has its own inflated-size cap, derived from the largest pack the 07 §8 schema allows, and the matching payload-character limit. The exact numbers are set when the M1b proof work starts (proposed until then).
- **Larger packs are files.** A pack above the link limit is never offered as a link; it is shared as a file (the drop zone, or a download). A pack can carry a disclosed envelope of up to 24 KB of mostly incompressible ciphertext, so such a pack can pass the link limit.
- **Copy** (derived; proposed, owner confirms at merge). Where a pack link is offered, the copy says that a link carrying a disclosed key is itself a disclosure (11 §5).

## 7. Browser counterparty: view and accept (P1, M2)

For a counterparty who has no agent yet (D-35, 02 F-15). Design is part of D2 (11 §6.5).

1. The **invite landing** (§4) decodes the invite locally and shows the inviter's name ("self-declared" or "verified domain", 04 §2.7), owner fingerprint and expiry. It cannot show a safety code: the code needs both sides' pairing messages (04 §3.6.1). Next to the "I use…" picker it offers **View and accept in browser**.
2. This hands off to the console origin with the invite still in the URL fragment (`https://console.…/accept#<invite>`). Keys then live on one origin, under the console's web-security controls (§2.3), and the invite origin stays a plain static page.
3. **Identity** works as for a new console owner (§2.1): a passkey with PRF, the owner seed generated in the browser, an encrypted backup to relays, and a **recovery kit offered** (recovery code fallback when PRF is unavailable). The page also generates a **browser agent** seed, wrapped the same way and included in the same backup and recovery kit, and the owner signs its agent card (harness label "browser"). The agent key is needed because receipts are signed by the recipient agent (05 §3.1).
4. **Pair:** accepting runs the normal pairing protocol (04 §3.6) from the browser. The confirm-contact screen shows name, label and owner fingerprint, and the user's passkey confirmation is the owner approval. Once the inviter's agent answers the handshake, both sides show the same safety code to compare through another channel; until then the page shows the pairing as waiting (04 §3.6.1).
5. **View:** the page syncs from relays and decrypts in the browser. It shows the thread: messages, offers with `terms` (with the changes between versions), files (fetched from the encrypted drop or the sender's storage and decrypted in the browser under the 04 §4 rules) and proof status.
6. **Accept or reject:** with one passkey gesture, the page sends a typed `accept` / `reject` quoting the `termsHash` (04 §3.4) and, for a notarized record, signs the `ACCEPTED` / `REJECTED` receipt with the browser agent key and submits it through a submitter. The gesture approves one commitment scope (04 §3.4.2, D-55), so a receipt for a record that arrives later is signed under it while the page is open and before the scope expires. The page says so: "Keep this page open, or come back before 20 Oct, to add your Accepted receipt." The browser has no background loop, so it never promises "automatically". The recipient pays nothing (receipts are prepaid, 02 §4). The human here is the owner, so this gesture is the commitment approval (D-31).
7. **Export** the proof pack (a proof of agreement for accepted terms) and open the verify page.
8. **Later:** signing in to the console with the same passkey shows this identity, and the owner can add a local agent or the desktop app (§2.2 Agents).

**Fetching files from the encrypted drop: CORS (M1-27a, IR-D48-1 F15d; proposed, owner confirms at merge).** Only `GET` of an object (`/v1/get/…`) and its preflight carry CORS headers. `Access-Control-Allow-Origin` echoes the request's `Origin` only when it is on the drop's configured list: the console origins, exact `https://host[:port]`, never `*` or `null`. The preflight allows method `GET` only, no request headers and no credentials, with `Vary: Origin` and a max-age of 600 s; any other origin or method gets 403 without CORS headers. Upload, PUT, commit, DELETE, report and health send no CORS headers at all, so no web page can call them cross-origin. Objects are served with `Cross-Origin-Resource-Policy: same-origin`, so other pages cannot embed them.

Scope: view, accept or reject, and export. Not a chat app (02 §6). Counter-offers or free-text replies from the browser: `DECISION NEEDED (owner)` (not in D-35; default: not offered).

**Zero knowledge holds:** the pages are static with no backend; the invite payload stays in the URL fragment, which browsers never send to a server; keys are generated and kept in the browser, wrapped with the passkey; decryption happens only in the browser. 4thTech sees page loads, and through the submitter only the signed receipt, which becomes public anyway (I-1 to I-3). Residual risk is the same as for the console (malicious JavaScript from a compromised host, 04 §7; mitigations §2.3); users who need more use a local agent or the desktop app. Passkeys bind to the console's domain, so the production domain choice applies (D-38).
