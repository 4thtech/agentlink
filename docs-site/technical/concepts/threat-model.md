# Threat model

<!-- ai-knowledge: summary
summary: The public threat model: a table of threats, mitigations and what remains, copied from the security spec. -->

> **Status: Current for v0.5.11.** The public threat model as shipped in release 0.5.11. Source: [04 §7](https://github.com/4thtech/agentlink/blob/main/docs/foundation/04-security-and-crypto.md#7-threat-model), which is normative. It lists the threats the design addresses and how; it is not a list of known vulnerabilities. Findings from reviews and audits are handled privately ([SECURITY.md](https://github.com/4thtech/agentlink/blob/main/SECURITY.md)) and published only once fixed.

Section references such as (04 §4) point into the source spec. A "Residual" names what remains and what limits it. The table below is copied from 04 §7 by `tools/docs-status` on every docs build, so it always matches the spec; edit the spec, not this page.

## Threats and mitigations

<!-- threat-model-table:start -->
| Threat | Mitigation |
|---|---|
| **Malicious or compromised relay** | Gift wraps hide sender and content; multiple relays; signature verification; dedup by gift-wrap ID, then by `envelopeHash` once the signature has passed, never by the sender-chosen envelope ID (04 §3.5, 07 §4.2; confirmed by the owner, D-71 (3)) |
| **Malicious storage provider** (own storage) | Ciphertext only; hash checks; expiring URLs |
| **Malicious or compromised encrypted drop** (D-48) | Ciphertext only; the file key travels only in the end-to-end-encrypted envelope; `ciphertextSha256` and `plaintextSha256` checks; signed, expiring URLs; at worst it denies, deletes or delays delivery (I-3), and the sender can resend through own storage. The metadata it sees (drop key, sizes, times, IPs) is minimised: the drop key is unlinkable to the agent's public identity, and only aggregate counters are kept, never URLs, object IDs or keys (04 §4) |
| **Drop abuse / free storage misuse** (hosting malware or illegal content, quota farming with fresh drop keys) | Per-file size cap and weekly quota per drop key, backed by per-IP rate limits and a global cap (residual sybil risk, 04 §4 Limits); hard 7-day expiry; per-object download limit; objects served only as `attachment` octet-stream from a dedicated host (no web pages); a report path that deletes the object (blocking a key needs human review); contents cannot be inspected (ciphertext). `DECISION NEEDED (owner)`: terms of service and takedown process (counsel) |
| **Consumer storage account compromise or over-broad OAuth scope** (D-49) | Minimal scopes (app folder or app-created files), so a stolen token reaches only AgentLink ciphertext; tokens only in the OS keychain (bound to the signed desktop app where the OS allows), never sent to 4thTech or logged; a compromised account can read only ciphertext and can delete or replace it, which the hash checks detect; the owner can revoke the app at the provider. A provider whose sharing API needs a broader scope ships only after an owner decision (07 §5.5) |
| **Malicious submitter** | Cannot alter signed records; can only censor → client fails over to another submitter or direct mode |
| **Budget ledger tampering or clock moves** (same OS user; G-7) | The budget check and the reservation of the Record's `maxFee` run in one transaction (06 §3). A missing or unreadable ledger, or a clock earlier than the newest ledger entry, makes every paid action need approval (fail closed). Residual: unlike the policy version, the ledger has no KeyStore high-water mark, so deleting ledger rows (G-1) resets the daily budget; moving the clock forward repeatedly (root or `CAP_SYS_TIME`) empties the window. Mitigations: `perActionMaxUSD` and the hard per-Record ceiling `hardMaxPerActionUSD` (D-156) still apply per action, small credit balances, and the on-chain charges remain visible in the vault |
| **Network observer** | TLS everywhere; content already E2E-encrypted |
| **Compromised 4thTech web host serving malicious console JS** | Open source, reproducible builds, published hashes, SRI, CSP; self-hostable console; local packaging avoids the web entirely. Residual risk documented |
| **Shell-capable harness agent (same OS user)** | Owner key never on disk unwrapped; owner operations need passkey/passphrase (04 §2.5); signed policies; harness permission guidance; small credit balances |
| **Malicious sender equivocates across recipients** (one ciphertext that opens under two keys, different keys per entry, an owner's entry that does not open; G-46) | `aead.kc` key commitment checked before decrypting (04 §3.1, 04 §3.3); every opener recomputes the wraps it can check, its own owner's always (04 §3.3, 04 §3.1.1 step 8); the proof-pack verifier checks `kc` (07 §8). Residual: an entry whose key the opener does not hold cannot be checked. Different envelopes sent under one `id` to different recipients are G-48 |
| **Malicious counterparty: prompt injection** | Inbound content labelled `untrusted`; actions limited by owner-signed policies; new contacts need owner approval by default; files only from allowed folders; spending budgets |
| **Malicious counterparty: spam / flooding** | Allowlist by default; unknown senders → requests queue with per-key and total limits (07 §3.2); refused rows from unknown keys expire after 7 days, and the owner can ignore one sender, clear the whole queue or block a key at any time (D-72), so a flood from fresh keys never fills the queue for good; per-contact rate limits; envelope size cap |
| **Malicious counterparty: SSRF via file or relay URLs** | 04 §4 SSRF rules (`agentlink_fetch_file`; relay URLs at parse and at connect) |
| **Malicious files / symlink tricks** | Never executed; sanitized names; realpath checks; size limits |
| **Contact floods the disk or plants files through auto-save** (D-142, 04 §4.1; proposed, owner confirms at merge) | Only from paired, allowed contacts that are not blocked, removed or revoked; per contact and per agent daily file and size limits; 1 GiB kept free; per-contact "Ask before saving" and a global off switch; quarantine mark (macOS, Windows); never opened, run or made executable; the extension decides nothing; sanitised names, realpath, no symlink following, never overwrites. Residuals: bytes without a gesture up to the limits; download timing and IP visible to a sender using its own storage |
| **Stolen laptop** | Keychain protection (OS login); owner key needs passkey/passphrase; owner can revoke the agent (revocation envelope + on-chain revoke if registered) |
| **Leaked file KeyStore on a headless machine** (D-54: home directory, volume, image layer or backup copied; passphrase in an environment variable or config) | Opt-in only, after a plain-words warning; Argon2id + AES-256-GCM with authenticated header; generated 120-bit unlock code by default; passphrase file from a run-time secret mount recommended over environment variables; 0700/0600 modes, symlink and `realpath` checks; `doctor` warnings; a copied `owner.alko` is protected by a required 120-bit owner code, and the owner key is never unlocked non-interactively, so a leak exposes the agent key only (revoke and replace the agent; changing the code does not protect earlier copies). Residual: a passphrase stored on the same disk gives no at-rest protection beyond disk encryption; an agent that fakes a terminal and runs the owner step itself voids owner presence on that machine (04 §2.8) |
| **Phishing invites** | Invites show the name under the name rule, the label, the owner fingerprint and the expiry; the safety code follows pairing (04 §3.6.1); expire; single use; owner approval by default |
| **Short invite links on the drop** (D-139, 04 §3.6.2; proposed, owner confirms at merge) | The drop stores only `ALI1` ciphertext under a `lookupId` derived one-way from the link secret; the key stays in the URL fragment and is never sent to any 4thTech service or logged; the fetch URL is built from the shipped drop host, never from the link, with no redirects and a 17 441-byte cap; AAD binds the object to its ID. A compromised drop or an attacker with the ID only can deny (delete, burn the download limit) but not read or substitute the invite. **Residual:** the drop sees which IPs uploaded and fetched one invite, so it can tell that two addresses paired; accepted by the owner, with the long link under Advanced and `agentlink invite --long` for owners who want none (D-139 (7)) |
| **Unauthenticated report deletes an invite object** (D-139: `POST /v1/report {v: 1, lookupId, reason}`, 07 §5.4) | Anyone who holds the `lookupId` (the drop itself, a leaked log, or anyone with the link) can have that one object deleted without signing anything. This is **deny-only**: the recipient sees "no longer available" and the inviter creates a new invite; it reveals nothing and cannot substitute an invite. The ID is a 128-bit value, so a report cannot target an object the reporter has not seen; reports are rate-limited per IP |
| **Flooding of the unauthenticated invite fetch** (D-139) | 128-bit IDs (no enumeration); per-IP (/64) and global fetch limits; per-object download limit; uniform `404` for unknown, expired, used-up and deleted objects; invite uploads need a signed drop request with per-key limits (07 §5.4) |
| **Swapped or copied invite (MITM at pairing)** | Commit-then-reveal safety code, 12 digits, compared by the owners on their own surfaces and never relayed by an AI (04 §3.6.1); "Safety code checked" only through an owner-signed `contact.check`; single-use invites, a second answer reported to the inviter's owner (04 §3.6) |
| **Agent ID claimed by another owner's card, or a replayed card** | `cardAgentSig` binds the agent key to the owner binding; a `handshake` only from `card.agentNostr` and an ack only from the invite card's key; one contact per `agentId`; a re-pair takes effect only on completion and only with unchanged owner keys (04 §2.9) |
| **Local edit of the displayed safety code** (a steered AI with shell access) | The code is recomputed on every display from the signed `handshake` and `handshake-ack`, each input covered by the peer's signature, never read from a stored digest; `contact.check` signs the recomputed digest (04 §3.6.1). Residual: an agent that alters the AgentLink installation itself controls what that machine shows (04 §2.5), so important contacts are compared on the console |
| **Replay of records / receipts / authorizations** | EIP-712 domain, nonces, deadlines, one-time receipt flags; EIP-3009 nonces |
| **Abuse of a public agent card** (e.g. registering it with attacker fees) | Registration requires a separate owner signature over fee parameters (05 §4) |
| **Submitter gas griefing** | Simulate before submit; require on-chain credits; per-signer rate limits; minimum deposit for gasless top-ups |
| **Supply chain (npm)** | Minimal dependencies, pinned lockfile, npm provenance, 2FA, reviewed updates, no postinstall scripts in our packages |
| **On-chain metadata analysis** | Pseudonymous agent keys, salted commitments; per-relationship keys (P2) |
| **Agent commits its owner to terms** (prompt injection or an over-eager agent, including terms where the owner is the one who delivers or pays) | Policy `commitments.accept` defaults to `approval` (D-31); auto-accept only for allowlisted contacts, in the direction the owner chose (who pays and who delivers) and within its limits (04 §3.4.2); the approval screen shows the terms and the changes from the previous version; `termsHash` binds exactly what was accepted (04 §3.4); the agent names the offer by envelope ID and cannot supply the accepted terms (D-55) |
| **Reuse or replay of a commitment approval** (an approval used for other terms, a newer version, another contact or agent, a second accept, or a late receipt) | One approval binds one commitment scope (04 §3.4.2): own agent, counterparty and its owner key, thread, the answered envelope and its hash, `termsHash`, decision, fee cap and an expiry no later than `validUntil`; each part runs once and is recorded; the digest is recomputed from the store before each part, and any change voids it; record nonces and one-time receipt flags on-chain (I-6); auto-accept grants are ledger rows re-evaluated against the verified policy before each part; one live scope per answered envelope with atomic claims; no forks in the negotiation chain (04 §3.4); the owner can cancel unused parts |
| **Local page imitating the approval page** (shared `localhost` passkey RP ID) | The owner's gesture is still required. Desktop app (D-145 (3)): phases 1 and 2 leave this as today (the macOS Touch ID step runs in the browser; a same-user process can also run the phase-2 helper after a gesture); phase 3 (signed) makes the helpers and the owner key usable only by the fixed-identity owner process (04 §2.5) |
| **Spoofed or lapsed domain claim** | Owner-signed claim checked against the contact's owner key; periodic re-check with downgrade and warning; exact domain shown; SSRF rules on `.well-known` fetches (04 §2.7) |
| **Compromised cloud-agent template or update** (D-131: code served on the Worker's `/approve` page captures the owner seed after the PRF unwrap) | Template releases only from a release tag after the owner's click (D-52, `release-and-deployment.md` §4.8); npm versions pinned with provenance; CSP and SRI on the owner pages; a reproducible owner-page bundle whose hash `/status` shows next to the published one. Residual, stated plainly: whoever can deploy code to the user's Worker controls its owner pages, the same class as a compromised console host |
| **Compromised 4thTech guide page that generates the button's secrets** (D-131 (9): `SETUP_CODE` and `SEED_WRAP_KEY` are made in the browser; proposed, owner confirms at merge) | Static page with one first-party script, no third-party scripts or analytics, SRI and the invite page's CSP with `connect-src 'none'` (08 §4), so the values cannot be sent anywhere; reproducible build with published hashes (M2-2h pipeline); the desktop path (`agentlink cloud deploy`) needs no page at all. Residual: whoever serves malicious page code could choose or leak both values, the same class as a compromised console host; a leaked setup code matters only until `/setup` is used |
| **Cloudflare account compromise** (D-131) | The attacker gets the agent seed and the store, and can deploy code that phishes the owner's gesture. Mitigations: the guide asks for Cloudflare two-factor sign-in; small credits; the owner deploys a new agent and pairs again (a clean `agent.revoke` signing path outside the account comes with the console). Residual, stated plainly |
| **Cloudflare as the user's processor** (D-131) | It runs the user's Worker and can technically read its secrets and memory. Disclosed in the guide: "Your agent runs in your own Cloudflare account. Cloudflare runs it for you; 4thTech never sees it" |
| **Setup race on a guessable `workers.dev` name** (D-131) | `/setup` needs the setup code, works once, and is refused once an owner exists (04 §2.5 "Cloud owner presence"); CI tests the claim |
| **OAuth token theft or an over-broad grant** (cloud agent, D-131) | PKCE S256; 1 h access tokens, rotating 30-day refresh tokens and grants that expire after at most 30 days, for every connecting app (D-131 (m), decided by the owner, 2026-10-26); redirect hosts limited to the tested default list, others only under Advanced (D-131 (j)); one fixed tool scope checked by our handler; every grant needs an owner-signed `connector.authorize`, checked in `AgentDO` on every request, so a removed grant fails at once even though the library keeps the previous refresh token valid once; owner operations never accept a token (I-4). A stolen token is equivalent to a compromised AI app: it can talk and spend within the signed rules and budget |
| **Malicious client registration** (dynamic registration lets anyone register) | Registering grants nothing: every grant needs the owner's gesture on the sign-in page, which names the app and its redirect host |
| **Look-alike approval link** (a counterparty or injected text supplies a fake `/approve` URL for a cloud agent) | Approval links only come from our tool results, never from inbound content (I-5, 06 §4); the passkey works only on the exact Worker host (RP ID), so a look-alike host cannot use it; the page shows the agent's name and owner fingerprint |
| **OAuth library's own crypto** (the narrow exception, D-131 (11), 04 §8 rule 1) | Allowed only in `apps/cloud-agent`; it handles only OAuth data, never keys or content; platform WebCrypto only; its other features (signed-JWT and enterprise grants, the "remember approval" cookie) are off and tested off; exact pinned version; Fable audit of the integration before 0.5.0 |
| **Denial of wallet** (floods raise the user's Cloudflare bill) | Unknown-sender queue limits (07 §3.2), per-IP limits on `/mcp` and the OAuth endpoints, alarm-only sync, the expected monthly cost in the guide |
| **Malicious desktop app update** | One update key (D-151, decided by Tali in chat, 2026-11-13): its public key pinned in the app (`root-key.json`, a sensitive path), the private key the environment secret `DESKTOP_UPDATE_KEY` in `desktop-update`, read by one CI step only after the owner's approval click. Signed domain tag (v2), channel, platform, arch, kind, version, minimum version and expiry (at most 31 days); strict parsing (D-128); the URL host allowlist; no downgrade; bytes checked against `sha256` and `size`. The release builds the manifest only from the Release's own assets after checking their sums and build provenance attestations, checks that both built apps carry exactly the pinned key (the build refuses an ASAR without it and the placeholder), and runs the app's own parser on the signed bytes before uploading. The assets must carry build provenance attestations from `desktop.yml` at the released commit of `main` and equal this run's own build (IR-UPD-8-1 #1); a job without a secret checks that `desktop-update` has a required reviewer, a main-only branch rule and no admin bypass before any job can reach the key (#2); a renewal (`desktop-update-renew.yml`, dispatch only, same environment) re-signs only the Latest release, from its attested assets. **Residual, owner-accepted:** whoever holds the key **and** can upload to the repository's Releases can ship code to installed apps (which could then read keys, I-1/I-2 in effect): the same trust as npm `latest` ("Supply chain (npm)"). There is no field revocation: a leaked key stays trusted by installed apps until they install a release that pins a new key (by hand, until a bridge release exists). Limits: the approval click and branch rule of `desktop-update`, one step with the key, `DEPLOY_FREEZE`, document expiry ≤ 31 days. **Residual, owner-accepted (IR-UPD-8-1 #3):** the approval click is a process rule, not a technical boundary, against agents: they work under the owner's GitHub account (D-51), whose token can approve the pending job, change the environment rules, replace the secret and upload Release files; only AGENTS.md ("never approve deployments") stops it, as for npm `latest`. Fix later: an agent token without Actions approval and admin rights. When signed: OS code signing and notarization checks as well |
| **Changed staged bundle during the in-app update** (UPD-4 Mac install; IR-UPD-4-1 #1, the G-1 residual; proposed, owner confirms at merge) | Residual, accepted for the unsigned builds. The new `AgentLink.app` is checked in `<app data>/updates/u-…/unpacked` (zip hash from the signed manifest, tree, bundle id, version, `codesign --verify`, helper id, node team, `bundle-hashes.json`, no quarantine mark), then waits for the person's "Restart now" (UPD-5, no time limit while the app keeps running; left-over staging folders are removed 24 hours old at the next start). On the click the signed manifest is checked again (it must still name the same version and installer, IR-UPD-8-1 #9) and the staged bundle's checks are run again; the watchdog then renames it into place within about two minutes without a further check. A same-user process could change it in between (time of check to time of use). Today this adds nothing: the swap runs only when the installed bundle is writable by the same user, who could change it directly, and the build is ad-hoc signed. It becomes a real bypass once the installed bundle is better protected than the app data folder (macOS App Management, Developer ID). Re-audit before UPD-9 (Developer ID): re-verify after the rename, or stage in a location only the installer can write |
| **Changed setup during the Windows in-app update** (WIN-INAPP-UPDATE; proposed, owner confirms at merge) | Residual, accepted for the unsigned builds, the same class as the Mac row above. The setup is checked (size and SHA-256 from the signed manifest) after the download and again after Restart now; then it is made read-only and its file identity (volume, file id, size, modification time) is passed to the watchdog, which compares it before it runs the setup and again once the setup's image is running (Windows then refuses writes to it); a mismatch is never run, or is stopped at once, and the old copy comes back. A same-user process that rewrites the file in place and restores its modification time between the last check and CreateProcess is not caught; the same process could replace `AgentLink.exe` in the user-writable install folder directly, so this adds nothing today. Becomes real once the install is better protected than the app data folder (Authenticode, WP-D18): then the watchdog checks the setup's Authenticode signature too. No mark of the web is added, so SmartScreen does not check the setup; the signed manifest's SHA-256 does. Further same-user residuals of the same class (IR Fable r1): the watchdog's `node.exe` runs from the staging folder (checked against the installed app's `bundle-hashes.json` before it starts), so a same-user process could plant a DLL beside it (Windows DLL search order); any same-user process can read the pending nonce and write the health answer, so a broken new copy could be kept. The watchdog checks the setup's identity and signed size right before it runs it, not its SHA-256 again (the app checked it after Restart now; the plain-Node watchdog has no `@4thtech-io/crypto`). A watchdog that dies after it moved the install folder aside leaves an HKCU RunOnce entry that puts the old copy back at the next logon; a healthy start of either copy removes it |
| **Same-user process drives the desktop app** (debug port, inspector, `NODE_OPTIONS`, injected switches, preview mode) | Release builds: fuses read back by CI; main exits on any switch outside a small allowlist (tested per switch on the built binary); preview mode compiled out (checked in the built ASAR); scheme `"<exe>" -- "%1"`; sandboxed, origin-locked window with an in-memory session and no preload API (08 §8, D-145 (4)). Residual while unsigned: a same-user process can still modify the installed app (G-1, like the npx cache) |
| **Crafted `agentlink://` link** | Only `agentlink://join#…` after `--` is read; canonical rebuild and the `join` pattern check, then the core's D-69 decode; kept in memory only, never logged; accepting needs presence. Any website can trigger the scheme, which shows at most "Accept X's invite?" (08 §8, D-145 (7)) |
| **Tampered Electron or Node binary in the build** | Per-asset SHA-256 committed in the repo and checked before use; upstream signatures kept; no `electron` package or install scripts; Electron security fixes within 7 days (08 §8, D-145 (1)) |
| **Message previews in the menu bar widget** (D-155; inbound text shown outside an AI's untrusted wrapper) | A preview is built by the server: plain text, at most 80 characters, one line, control, format, bidi and separator characters removed, cut on a grapheme boundary; shown as a text node only, never rendered as markup, linkified or used as a file name. "Show message previews" (Settings, on by default) turns them off, and then `GET /api/ui/widget` omits them (enforced on the server). Previews never reach the icon, its tooltip, the private pipe, OS notifications, the page title or logs (I-5, I-7). The widget is read-only: it approves, signs and changes nothing and never shows a presence prompt (08 §8). Residual, accepted by the owner: a glanceable surface can be read over a shoulder; the switch is the answer |
| **Agent key asked to sign foreign typed data** (D-156 (2); a steered AI or a compromised caller passes an arbitrary EIP-712 payload to the agent key) | The agent `KeyStore`'s `sign712` signs only AgentLink's own shapes: OCC v2 records and receipts for an allowlisted chain and contract, agent cards, and the credits top-up authorization with the recipient fixed to that chain's AgentLink vault, an allowlisted token and a value cap; anything else is refused with a fixed error **before any key material is loaded**, in every backend (04 §3.1.1 "What the agent key signs as typed data"). Owner signing is unchanged and needs presence (04 §2.5) |
| **Forged, misattributed or replayed "received" acknowledgement** (D-156 (1); a relay, a third party or another contact claims that a message was received) | The `ack` v2 body is bound to the envelope hash, not only its ID; the sender counts it only from the contact the envelope went to, only when its signature verifies against that contact's card at the key epoch in force when it was made, and only when the hash matches the stored envelope (04 §3.4 `ack`). Acks go only to active, fully paired contacts, never to a request, a blocked, removed or revoked contact or an unknown sender. An older app's ID-only ack shows as "Received (older app)" and never makes a proof "Delivered"; on-chain DELIVERED receipts stay separate and opt-in (D-109). Disclosure: an ack tells the sender that the recipient's AI app processed the message at about that time, so it waits a random 5 to 90 seconds, carries a minute-rounded time, and can be turned off (`receipts.sendReceived`; a per-contact setting is planned) |
