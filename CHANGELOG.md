# Changelog

All notable changes to AgentLink are documented in this file.

The format is based on [Keep a Changelog 1.1.0](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning 2.0.0](https://semver.org/spec/v2.0.0.html). How versions, tags and releases work is described in [`docs/process/versioning.md`](docs/process/versioning.md). Until 1.0.0 (the M3 mainnet beta), a minor version may contain breaking changes; each is marked **BREAKING:**.

## [Unreleased]

### Added

- Monorepo skeleton (M0-2d): pnpm workspace with Turborepo, strict ESM TypeScript with project references, ESLint, Prettier, Vitest and Changesets; a stub package for every directory in the repository layout; manifest checks (MIT licence, no install scripts) inside `pnpm lint`; and CI strict mode (`.github/ci-strict`), so a missing root script now fails CI. All packages are private stubs and nothing is published yet.
- Redacting logger `@agentlink/log` (M0-8): zero-dependency structured logging for Node, browsers and Workers that redacts secrets by field name and by value shape at every level and logs URLs as their origin only, and a secret-canary test helper that fails CI when a known fake secret reaches any log line. Console output is banned outside the logger and the CLI's user-output channel.
- Architecture boundary guards (M0-10): package layering (which package may import which, no cycles), primitive libraries (`@noble/*`, `@hpke/*`, `nostr-tools`, `viem`, `aws4fetch`) and `crypto.subtle` confined to their packages, Node built-ins confined to `@agentlink/node` and `apps/cli`, and a per-package runtime-dependency allowlist where every entry carries a justification. Enforced twice: ESLint zones (including dynamic `import()`, `require()` and relative paths that leave a package) and `tools/deps-check`, which runs in `pnpm lint` and therefore in `ci-gate`. The policy lives in `tools/deps-check/policy.mjs`.
- Cross-runtime test-vector harness (M0-9): `pnpm vectors:check` runs every vector suite in Node, Chromium, Firefox, WebKit and workerd. Each runtime must report its own identity and pass every committed case, and the run may not change anything under `test-vectors/`. CI also checks every committed vector file against its independent generator. Includes the vector file format and schema, a placeholder SHA-256 suite from published NIST and RFC values, and runbook RB-06. There are no protocol vectors yet.
- Protocol test vectors for M1a (M1-1h): 15 suites, 975 cases (471 of them rejection cases). They come from independent Python generators with hash-pinned dependencies (`cryptography`, `coincurve`, `pycryptodome`, `pyhpke`, `rfc8785`). They include the official RFC 5869, RFC 4231, RFC 8785, RFC 9106, RFC 9180, BIP-340, EIP-712 and NIP-44 v2 vectors. AgentLink cases cover key derivation, canonical encodings, the envelope (hash, AEAD, signature, strict structure), the CEK wrap (including every small-order X25519 point), `SignedOwnerAction`, the AgentCard and `cardSig`, the pairing proof, the safety code (signed handshake and ack recomputed), agent ID and fingerprints, and the `ALKS` and `ALKO` file formats, each with rejection cases. Suites whose code has not landed are pending (`test-vectors/pending-suites.json`): CI warns for each one, fails once its module exists, refuses to let the list grow back against `main`, and a release fails while an M1a suite is pending. A suite may declare fewer runtimes only by citing a spec runtime table (`keystore-file`: Node). CI installs the generator dependencies and checks every file byte for byte.
- Crypto base layer `@agentlink/crypto` (M1-1a): strict canonical encodings (bare and `0x` lowercase hex, base64url without padding, decimal uint256, UTF-8), each rejecting every non-canonical form instead of normalising it; SHA-256 and keccak-256 through `@noble/hashes`; BIP-340 tagged hashes with the protocol tags `agentlink/envelope/v1` and `agentlink/owner-action/v1`; RFC 8785 JSON canonicalisation with a strict parser that rejects duplicate keys, lone surrogates and non-finite numbers; a constant-time byte comparison; `randomBytes` from `globalThis.crypto.getRandomValues` only; and a best-effort `wipe()` whose limits are documented. The `jcs` and `tagged-hash` vector suites now run in all five runtimes.
- Key derivation and public identities in `@agentlink/crypto` (M1-1b): HKDF-SHA256 and the exact derivation of the agent keys (EVM, Nostr, encryption and drop keys, with the secp256k1 rejection loop; the EVM key exists only at epoch 0), the agent ID as a lowercase `0x` address (EIP-55 checksum for display only), the encryption key `kid`, a public identity bundle that never contains the drop key, BIP-340 sign and verify helpers that reject keys off the curve and out-of-range signatures, and owner and agent fingerprints with their short, long and domain-claim forms. Every function that takes a master seed or a secret key is exported only from the restricted subpath `@agentlink/crypto/keystore`, which the boundary guards allow only for KeyStore backends (`packages/node`) and the vector harness. The `hkdf-derive` (with the agent ID cases), `bip340` and `fingerprint` vector suites now run in all five runtimes.
- Policy, approval and proof types `@agentlink/types` (M1-2b): the policy document in its strict JSON form (06 §3, G-32), with the exact defaults, per-contact proof rules, sorted agent-ID lists and USD amounts as strings in one spelling; it now replaces the placeholder inside `policy.set`. An exact USD helper (integer micro-dollars: parse, compare, add, round up to cents, compare a terms price of any size). The G-7 constants (clock skew, owner-action lifetimes, approval TTL, nonce retention, budget window). A strict `approval-request` context for each approval tool, with the commitment scope, the fee and the policy rules that asked, and the 24-hour request TTL checked. ProofPack v1 (07 §8) with the Record and Receipt JSON forms, ProofStatus (06 §2.4) and the common tool-result shape (06 §1). Anything malformed is rejected, never completed with defaults. Some choices are proposed for spec confirmation (listed in the PR).
- EIP-712 and the AgentCard in `@agentlink/crypto` (M1-1e): EIP-712 typed-data hashing (checked against the EIP's own example and, in the unit tests, against viem); canonical secp256k1 ECDSA signatures, `0x` + r‖s‖v with low `s` and v 27 or 28, where a high `s`, v 0 or 1, a wrong length or non-canonical hex is refused before recovery; the AgentCard type under the chain-agnostic domain `{name: "OCC AgentCard", version: "1"}`, a strict parser for the card JSON form (and for its JSON text, refusing duplicate keys and `1.0`, `1e3` or `-0` on the token), `sha256(JCS(card))`, and `cardSig` and `cardAgentSig` verification, with both signatures required for an invite or handshake card; signing is only in `@agentlink/crypto/keystore`. viem is a test-only library in `packages/crypto` (deps-check and ESLint refuse it in runtime source and runtime dependencies). The `eip712` vector suite now runs in all five runtimes.
- Build plan "At a glance" (building blocks, stages, external services) and plain-language explainers on messaging, files and payments under `docs/explainers/`.
- Public documentation source under `docs-site/`: a user guide and technical docs (one GitBook space each, for publishing through Git Sync), organised by Diátaxis. Concept, security and pricing pages describe the published design; every other page is an outline marked planned with the version that fills it in. Upkeep rules in `docs-site/MAINTAINING.md`, a docs pass per milestone (backlog cards DOCS-M1a to DOCS-M3), and a Definition of done rule that a milestone or release is done only when the public docs are updated.
- Process (DOCS-RB): runbooks for every repeatable procedure (`docs/runbooks/`), lessons learned (`docs/lessons/`), a role-based "Start here" map with a time-boxed onboarding track (`docs/README.md`), and a `GEMINI.md` pointer so Gemini CLI loads `AGENTS.md`.
- Design drops D1 and the first pass of D2 (DESIGN-D1): brand assets (logo, app, tray and UI icons, colours, social images), design tokens in four themes with Geist fonts, in-chat and terminal copy, 31 component specs with a reference bundle, 46 screens (local approvals app, owner console, desktop apps, cloud agent, verify, invite, pay, pricing) and the live sources, under `docs/design/` with a `MANIFEST.md` per folder. Status recorded in `docs/design/README.md`: D1 delivered with partial points, D2 partial (no prototypes or rationale notes yet).

### Changed
- Backlog (review IR-M1-3b-1): M1-3a and M1-3b are done in the private contracts repo (merged 2026-10-14). The review's follow-ups are carded: fee-token configuration checks and a runbook step on M1-3g and M1-14, the Notary payer rule on M1-3d, ABI release and spec notes on M1-3f, and client, docs and runbook notes on M1-4b, M2-2d, DOCS-M1b and M3-9.
- Specification (review IR-M1-2b-1, proposed; owner confirms at merge): a missing, invalid or unverifiable policy now fails closed once any policy version has been applied (G-6): owner approval for every paid, commitment and owner-gated action, unknown senders queued, no contact rule or auto-accept, never the defaults. `ProofStatus.fee.token` is the fee token address (`0x` lowercase) and `fee.amount` the token base units as a decimal string, like the Record's `feeToken` and `maxFee`; the proof pack `signer` gains `cardSig`. **BREAKING:** `agentlink_get_approval` returns `approval` instead of `status` for the approval state, next to the common `status: "ok"`. New backlog card M1-1h-c regenerates the `sign-policy-set` vector.
- Specification (review IR-M1-2a-1, proposed; owner confirms at merge): one canonical encoding per binary value (04 §2.4.1). Nostr keys and signatures are bare lowercase hex, EVM values (addresses, `bytes32`, signatures, EIP-712 digests) are `0x` + lowercase hex, digests signed only under Nostr keys (`termsHash`, `actionDigest`, file hashes) are bare hex, and other bytes stay base64url, with a per-schema-path table and the overloaded names listed; values are compared as bytes, and any other form is rejected. **BREAKING:** the `proof` body's `recordId` and `salt` change from base64url to `0x` hex, matching the proof pack, and a commitment scope's `envelopeHash` gains `0x`. Also: the AgentCard JSON form is fixed, the `approval` body carries `approval.cancel` (D-55), relay URLs get SSRF rules (IP literals and local hosts rejected at parse, resolved addresses checked at connect), and the vector-blocking details are pinned: the pairing proof is keyed by an HKDF-derived `proofKey` that the inviter stores instead of a hash of the secret, its input bytes, canonical low-s ECDSA signatures, relay connections pinned to the checked globally routable address, the Argon2id password input for generated codes (the 15 decoded bytes) and the `ALKO` owner-wrap layout (04 §2.8).
- Secret scan: `.gitleaks.toml` keeps the default rules and allowlists only the public test-vector data files, which hold published test keys.
- Process (CHORE local-red-evidence): S2 tests-first evidence is now a local red run (`RED (expected):` commit with its SHA, command and output excerpt in the PR, never pushed on its own) that the independent reviewer reproduces, instead of a red CI run, which e-mails the owner (LL-14).
- CI and process (CHORE CI-PUSH): CI now runs on every branch push (except `sync`), so tests-first red runs, lint and tests show before a PR exists. Pull requests are opened only after the independent review passes, already carrying the `IR-…` line, so `review-gate` is green on its first run; task claims move from draft PRs to `board.md` rows with the branch name. Once a PR exists, each push runs CI twice (push and pull request).
- Process (D-58, D-59): the owner confirmed the owner-operation bodies (G-29: `SignedOwnerAction`, permanent per-agent revocation) and the contract roles and delays (G-3: 7-day delays, two ops hardware keys, a paused mainnet launch, with the pause residual risk in the M3-1 audit scope); README status updated for the M0 skeleton work.
- CI: `review-gate` fails fast on draft PRs with a one-line reason instead of a full set of errors; it runs in full once the PR is marked ready.
- Specification (G-23, G-28, proposed; owner confirms at merge): `agentId` is the agent's EVM address (`0x` + 40 lowercase hex), checked against the seed on every load. Invites and handshakes carry `cardAgentSig`, and a handshake is accepted only from the card's own agent key. A re-pair takes effect only when it completes. Object keys use a random per-agent prefix, and owner and agent fingerprints are defined for display only. **BREAKING (pairing):** the safety code becomes commit-then-reveal: invite `codeCommit`; handshake `codeNonce`, `codeCommit` and `inviterCardHash`; ack `codeReveal`, `handshakeHash` and the inviter card. It is 12 digits from a tagged hash of both cards, the invite ID and both nonces, and appears only after pairing completes. Owner surfaces recompute it from the two signed pairing messages, never from a stored value, and MCP results never carry it (`safetyCode` becomes `pairing` and `safetyCodeChecked`). It is marked checked only by an owner-signed `contact.check`.
- Specification (review IR-M1-3a-1, proposed; the owner confirms at merge): OCC v2 events and function names. 05 §6 now gives the parameters of every vault and Notary event and adds `Paused`/`Unpaused` (with the caller), `TreasuryChanged`, `MinDepositSet`, `IntegratorFeeCapMultipleSet`, `IntegratorChanged` and `IntegratorWithdrawn`; the error `Paused()` is renamed `EnforcedPause()` because an event and an error cannot share a name, and pausing while paused (or unpausing while not paused) reverts, as in OpenZeppelin, with the new `ExpectedPause()`; `MultipleAboveMax()` covers an integrator multiple above 10. New 05 §5.2 lists the restricted function names the interfaces use. Backlog cards M1-3b, M1-3d, M1-3e and M1-3g gain the review's carry-forwards: initial vault configuration in the initializer with no deployer-only window, role tests against the real contracts, and the open Lows.
- Specification (G-3, D-59): the OCC v2 AccessManager role map (05 §5.1) with one role per power and delay, holders per environment, grant delays, a cancel-only guardian and 7-day target admin delays. AccessManager administration, module registration and every contract upgrade now take 7 days, because any module can charge credits. Lowering and raising the fee cap are separate functions. Only the Safe can unpause, and mainnet contracts start paused until the configured delays are in effect. Removing a module is immediate (Safe, `PAUSE_ADMIN`), registering one takes 7 days. Pause never blocks `withdraw`, `withdrawIntegrator`, `sweep` or the Registry `revoke` (resolves G-39). Clients approve exact token amounts only. Two dedicated ops hardware keys hold `PAUSER` and `GUARDIAN`, and `PAUSE_ADMIN` revokes either at once.
- Specification (G-29, D-58): owner operations use one owner-signed object (`SignedOwnerAction`, 04 §2.5.1) from the local UI, the CLI and the console; 04 §3.4.1 fixes the bodies of `approval-request`, `approval`, `policy`, `revoke`, `card-update` and `handshake-ack`, who may send each, and how receivers check them.
- Specification (G-7, G-32, proposed; owner confirms at merge): owner-action lifetimes are fixed (300 s skew on `issuedAt`; a maximum lifetime per op, from the request's expiry for `approval.decide` to 7 days for `approval.cancel`; nonces kept 30 days), approval requests expire after 24 h, and `dailyBudgetUSD` becomes a rolling 24-hour window, checked and reserved (at the Record's maximum fee) in one transaction and failing closed on a broken ledger. `approval.cancel` can also void an approved approval that has not been used. The policy gains per-contact proof rules (`contactRules`), which "Remember for this contact" on a proof approval creates as an owner-signed policy change; it is no longer offered on new-contact approvals. **BREAKING (policy document):** the policy JSON form is now exact, with every key required, USD limits as decimal strings instead of numbers (one spelling for every USD amount, so `maxFeeUsd` `"0.10"` becomes `"0.1"`), contact lists as sorted agent IDs, and `allowKeyDisclosure` limited to `approval` or `deny`.
- Process (D-57, proposed; amends D-29): public docs are published continuously from `docs-site/` on `main` through GitBook Git Sync (no editing in GitBook), with an honest status line on every page; `docs-site/**` is security class S1; changes to the publishing setup are owner-only; rollback is a revert of the PR.
- Process (D-52): one automated delivery pipeline for every task (develop, independent audit, green required checks, auto-merge). S2 and sensitive paths need only Tali's "merge" in chat, with no non-author GitHub approval. Services (Workers, sites) now deploy to production automatically once staging and smoke tests are green, replacing the owner approval click of D-25 for them; npm `latest` keeps the owner's approval click; `DEPLOY_FREEZE` still halts everything. New `docs/process/delivery-process.md`: roles, 14-step lifecycle, safety nets, owner go-ahead model and definition of done.
- Specification (D-48): files over 12 KB go through a zero-knowledge 4thTech encrypted drop by default (ciphertext only, signed uploads, 7-day expiry, per-agent quotas), so file exchange needs no setup; own storage becomes optional. Resolves D-13 and amends D-05 and core principle 5.
- Specification (D-49): one-click Google Drive, Dropbox and OneDrive storage connectors are planned for the M2 desktop apps, with OAuth tokens kept only in the OS keychain; S3-compatible storage stays the Advanced option.
- Specification (D-50): phased revenue operations: a monthly revenue report from on-chain events in beta, an internal read-only finance dashboard later, and invoices on request through opt-in billing profiles.
- Specification (review IR-D48-1): the encrypted drop uses a dedicated drop signing key, encrypts each file once and sends the ciphertext hash at commit, keeps no request URLs or signatures in logs, and follows `files.deleteAfter` (default: keep until expiry); consumer-connector links are revoked at expiry on a best-effort basis; `apps/drop/**` is S2.
- Specification (D-54): on machines without an OS keychain (containers, WSL, SSH sessions), users can opt in to a passphrase-locked file for the agent's identity, unlocked from a run-time secret file or an environment variable; the keychain stays the default, and approvals still need an owner code typed in the owner's own terminal, or (from M2) the owner's own device. Resolves G-31.
- Specification (D-56): the product name is AgentLink, by 4thTech, with working domain myagentlink.xyz (final after the trademark check); the design brief now covers the full brand system and every surface per platform (desktop apps for macOS, Windows and Linux, cloud agent pages, terminal copy, printed proof records), and `docs/design/claude-design-handoff.md` is the single file to give Claude Design.
- Process (D-51, simplified): agents work under the owner's GitHub account; code-owner review is not required and Denis's approval is optional. S0/S1 pull requests auto-merge when all checks are green; S2 and sensitive-path pull requests merge only after CI, the independent AI review and the owner's explicit go-ahead (a process control, revisited before mainnet).
- Specification (D-53): the MCP tool surface is frozen before 0.1.0 at 13 `agentlink_`-prefixed tools with MCP annotations and `approvalId` on every tool that can need approval; one invite link installs AgentLink and pairs; agents check AgentLink at session start (counts only) and offer a handoff at session end.
- Specification (D-55): agents negotiate with two dedicated tools, `agentlink_propose_terms` and `agentlink_respond_to_terms` (accept, reject, counter), instead of typed offers through `agentlink_send`, bringing the frozen tool surface to 15; one owner approval, bound to the exact terms, contact, conversation and expiry, now covers both the acceptance and its Accepted receipt, and is void if the terms change; terms now state who pays and who delivers, and auto-accept applies only in the direction the owner chose.

## [0.0.1] - 2026-10-12

M0 Foundations: specifications (spec pack v0.3), development and audit process, CI/security workflows, versioning framework, agent instructions; no product code yet.

### Added

- Specification pack under `docs/foundation/`: product, architecture, security and cryptography (invariants I-1 to I-10), OCC v2 contracts, MCP server, SDK/transport/storage, clients, build plan and design brief, with a decision log (D-01 to D-44).
- Development process (orchestrated AI agents, task lifecycle, definition of done), audit rules (security classes S0 to S2, independent reviews) and a sync protocol for collaborators, under `docs/process/`.
- Release and deployment process: continuous delivery to staging and testnet, one owner approval click for production, rollback matrix and `DEPLOY_FREEZE`.
- GitHub Actions workflows for CI, security checks, secret scanning, pull-request hygiene, the review gate and the release pipeline (npm trusted publishing with provenance), all pinned to commit SHAs and dormant until the monorepo skeleton exists.
- Versioning framework (D-43): SemVer 2.0, one product version during beta, milestone-to-version map, npm `next` and `latest` channels, wire-format compatibility table and this changelog.
- Agent instructions (`AGENTS.md` and the per-tool files that point to it) and the backlog of task cards.
- Public repository files: README with status, `LICENSE`, `SECURITY.md`, Renovate configuration and the documentation map (D-44).

### Security

- Audit of the CI and release workflows: actions pinned to full commit SHAs, least-privilege token permissions per job, no untrusted event data in scripts, no long-lived npm token, and publishing only from `main` through GitHub Environments with provenance.
